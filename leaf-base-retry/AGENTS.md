# AGENTS.md - leaf-base-retry

本文档用于指导 `leaf-base-retry` 模块后续迭代开发。修改本模块时，优先保证重试语义稳定、失败恢复可预期、日志可观测，并避免无关重构。

## 通用硬性规则

1. 每次修改只能触碰当前 Maven 模块；确需跨模块时，先说明触发原因、受影响模块、替代方案和最小改动集合。
2. 现有代码已经在生产环境使用，不得随意更改对外接口规范、配置语义、默认行为、异常语义或序列化契约；必须变更时，同步补充兼容说明、迁移路径和回归测试。
3. 在确保原有功能正确的前提下完善实现；修改既有逻辑前，先用测试锁定当前成功、失败、空值、边界和回归路径。
4. 基础框架代码必须优先审查性能、线程安全、资源释放和并发可见性；线程池与虚拟线程都能满足需求时，优先使用虚拟线程。
5. 空值处理必须支持 JSpecify 规范：新增或修改 API、DTO、配置属性、回调、集合元素和异步结果时，明确 `@NullMarked`、`@Nullable` 或等价约束，让空值语义可被 IDE、编译检查和测试验证。
6. 严格遵循测试驱动最佳实践：先写或调整能暴露问题的测试，再实现最小代码变更，最后运行模块级验证命令。
7. 涉及改动的点都要检查测试用例是否完整；覆盖不足时补齐成功、失败、异常、空值、边界和回归场景。
8. 功能只有在 Spring Boot 应用运行后才能验证时，使用 `@SpringBootTest` 或等价方式模拟真实启动后的 Bean 装配、条件配置、AOP、监听器、异步流程和配置绑定。
9. 修改线程安全或性能相关代码时，必须补充严格测试；覆盖并发访问、重复执行、超时、取消、资源释放和关键指标，无法自动化时在提交说明写清手工压测命令、样本规模和观察指标。
10. 所有 `log` 日志内容必须使用 ASCII 字符，避免不同运行环境、终端编码或日志采集链路出现乱码。
11. 不要随便把已存在代码抽取成单独方法或类；只有抽取后的逻辑至少被两个位置复用，或能显著降低复杂度且不破坏语义时，才允许抽取。
12. 删除方法、类、变量上的冗余注释；清理 Javadoc 中重复、空泛或仅复述签名的信息，只保留语义说明、边界条件、异常约定等必要内容。
13. 复杂方法、复杂类、公共扩展点或使用方式不直观的能力，应补充必要 Javadoc；使用门槛较高时，给出简短使用示例。
14. 精准命令胜过陈词滥调：直接给出 `mvn -pl 当前模块 test`、`rg "类名|方法名" 当前模块/src/test` 这类具体步骤，避免“确保代码质量”“提升项目可维护性”等抽象套话。
15. 控制 `AGENTS.md` 长度与结构，建议保持在 200 行以内；规范继续增多时，在子目录创建领域指南，本文件只保留入口链接和必须遵守的红线。
16. 持续优化迭代：`AGENTS.md` 是动态文档；当 Agent 的实际输出与预期目标出现偏差时，把偏差改写成下一次可执行、可检查的规则。

## 1. 模块定位

`leaf-base-retry` 是 Maple Leaf Framework 的通用重试基础模块，主要提供：

1. 基于 Spring Framework Retry API 的统一重试配置（`GXRetryConfig`）。
2. 可编程重试工具（`GXRetryUtil`），支持同步、异步、恢复回调、自定义异常重试策略。
3. 重试生命周期监听（`GXRetryListener`），用于记录重试开始、失败、成功、耗尽、中断、超时等事件。
4. 回调与上下文抽象（`GXRetryCallback`、`GXRecoveryCallback`、`GXRetryContext`）。

不在本模块内承载具体业务流程、业务补偿编排或业务域异常语义。

## 2. 目录职责

1. `config`：重试模板和重试策略构建逻辑。
2. `util`：对外主入口工具，封装多种重试调用方式。
3. `listener`：重试过程观测与日志行为。
4. `callback`：重试执行回调、恢复回调接口契约。
5. `context`：重试上下文对象与属性传递能力。

## 3. 强制开发规则

1. 所有 `log` 日志内容必须使用 ASCII 字符，禁止新增或保留非 ASCII 日志文案。
2. 涉及改动的点，必须同步检查测试用例是否完整覆盖；覆盖不足时必须补充测试。
3. 不要随意把已存在代码抽取成单独方法或类；仅当抽取后可被两个及以上位置复用时才允许抽取。
4. 删除方法、类、变量上的冗余注释，避免注释重复描述代码字面含义。
5. 清理 Javadoc 中的冗余信息，仅保留必要文档；复杂方法、复杂类、对外扩展点可保留必要 Javadoc，并在必要时加入简短使用示例。
6. 变更重试默认参数（次数、间隔、倍率、最大间隔）前，必须评估兼容性与调用侧影响。
7. 变更异常重试映射（include/exclude）前，必须评估是否会导致“应快速失败却被重试”或“应重试却提前失败”。
8. 每次修改都只能修改当前 Maven 模块，不得修改其它模块。
9. 现有代码已经在生产环境使用，不得随意更改对外接口规范、默认行为或异常传播语义。
10. 本模块作为基础框架能力，代码性能、并发正确性和线程安全性必须优先评估。
11. 在线程池与虚拟线程都能满足需求的场景中，优先使用虚拟线程。
12. 严格遵循测试驱动最佳实践，优先通过测试描述预期行为，再进行实现或修复。

## 4. 测试要求

1. 任何功能改动必须覆盖成功路径、失败路径、异常路径、边界条件。
2. 严格遵循测试驱动最佳实践；新增功能或修复缺陷时，优先补充能暴露目标行为的测试，再编写或调整实现。
3. `GXRetryUtil` 相关改动至少覆盖：
   - 默认重试参数行为。
   - 自定义重试参数生效。
   - 指定异常可重试/不可重试。
   - 恢复回调触发条件与上下文内容。
   - 异步重试封装异常行为。
4. `GXRetryConfig` 相关改动至少覆盖：
   - 参数校验上下界。
   - `RetryPolicy` include/exclude 生成逻辑。
   - 默认重试异常映射回归检查。
5. `GXRetryListener` 相关改动至少覆盖：
   - 不同重试阶段回调触发。
   - cache 清理逻辑与边界。
   - 不同日志级别下分支行为。
6. 如果功能依赖 Spring 容器、自动配置、AOP 代理或 Bean 装配，测试必须使用接近真实运行形态的 Spring Boot 启动测试（如 `@SpringBootTest`），不能只做纯单元测试。
7. 至少保证模块级测试命令可执行：`mvn -pl leaf-base-retry test`。

## 5. 变更前检查清单

1. 是否影响 `GXRetryUtil` 对外重载方法语义或异常传播语义。
2. 是否影响 `GXRetryContext` 的 `retryCount`、`lastThrowable` 和属性读取行为。
3. 是否影响 `GXRetryConfig` 的默认值、参数校验或异常映射。
4. 是否引入了非 ASCII 日志内容。
5. 是否出现了不必要的方法/类抽取。
6. 是否移除了冗余注释和冗余 Javadoc，并仅保留必要 Javadoc/示例。
7. 是否已补充并运行与改动点匹配的测试。
8. 是否只修改了 `leaf-base-retry` 当前 Maven 模块内的文件。
9. 是否保持生产环境已使用的对外接口规范、默认行为和异常传播语义稳定。
10. 是否评估了性能、并发正确性和线程安全性影响。
11. 是否在适合的异步/并发场景中优先考虑了虚拟线程。
12. 是否遵循测试驱动最佳实践，先用测试描述目标行为再调整实现。

## 6. 提交说明建议

1. 涉及重试策略变更时，PR 描述必须说明行为变化、兼容性影响和回滚方式。
2. 涉及异常映射变更时，PR 描述必须明确“哪些异常会重试、哪些不会重试”。
3. 提交前确认新增/修改日志均为 ASCII。
4. 提交前确认测试已覆盖改动点，并在 PR 中说明关键验证结果。
