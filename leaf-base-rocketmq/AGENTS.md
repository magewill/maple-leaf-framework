# AGENTS.md - leaf-base-rocketmq

本文档用于指导 `leaf-base-rocketmq` 模块的后续迭代开发。修改本模块时，优先保持 RocketMQ 配置装配、消息发送语义和对外发送契约的兼容性，避免与当前职责无关的重构。

## 1. 模块定位

`leaf-base-rocketmq` 是 Maple Leaf Framework 的 RocketMQ 基础能力模块，当前负责：

1. `rocketmq` 配置读取与装配，支持本地 YAML 配置和 Nacos 配置两种来源。
2. RocketMQ 消息发送请求模型定义，包括主题、标签、消息体、延迟时间和消息 Key。
3. 基于 `RocketMQTemplate` 的统一发送服务，封装普通发送、同步发送、异步发送、单向发送和延迟发送。
4. 对发送前参数做基础校验，对发送结果做统一判定，并将异常包装为框架业务异常。

本模块当前不承载消息消费监听、业务路由编排、事务消息编排或复杂重试补偿逻辑；如需新增这些能力，必须先重新评估模块边界，并同步更新本文件。

## 2. 目录职责

1. `dto/inner`：RocketMQ 内部请求模型，承载发送参数和基础构造逻辑。
2. `properties/local`：本地 `rocket-mq.yml` 配置装配入口。
3. `properties/nacos`：Nacos `rocket-mq.yml` 配置装配入口。
4. `service`：对外发送服务契约。
5. `service/impl`：基于 `RocketMQTemplate` 的发送实现、参数校验和结果判定。
6. `src/test`：发送服务的 Spring Boot 测试基线，验证容器装配与关键发送路径。

## 3. 强制开发规则

1. 所有 `log` 日志内容都必须使用 ASCII 字符，禁止新增或保留非 ASCII 日志文案。
2. 涉及改动的点，必须同步检查对应测试用例是否完整覆盖；覆盖不足时必须补充测试。
3. 不要随意将已存在代码抽取成单独的方法或者类；只有当抽取后的逻辑可以被两个及以上位置复用，或确实显著降低复杂度时才允许抽取。
4. 删除方法、类、变量上的冗余注释，避免注释重复描述代码字面含义。
5. 在复杂的方法、类、对外扩展点上适当补充 Javadoc；必要时加入简短使用示例，便于后续使用者参考。
6. 变更发送入口时，必须保持 `GXSendRocketMQService` 现有方法语义稳定；若要调整返回值、异常语义或参数约束，需先评估兼容性并更新文档。
7. 变更消息目的地拼装规则时，必须确认 `topic`、`tag` 的去空格、空标签处理和 `topic:tag` 约定不被意外破坏。
8. 变更 `messageKey`、`body`、`deliverTime` 的处理逻辑时，必须评估对上游调用方和 RocketMQ 控制台排障方式的影响。
9. 本模块当前聚焦发送能力，新增功能时优先复用 `RocketMQTemplate` 与现有契约，避免平行引入另一套发送抽象。

## 4. 测试要求

1. 任何功能改动都必须先检查现有测试是否覆盖成功路径、失败路径、异常路径和边界条件。
2. 测试用例要覆盖全面；如果功能依赖 Spring Boot 应用启动后的 Bean 装配、自动配置、条件注解、生效顺序或发送服务注入行为，测试必须使用接近真实运行形态的 Spring Boot 启动测试，例如 `@SpringBootTest`。
3. 以下改动必须重点补测：
   - `GXSendRocketMQServiceImpl` 的参数校验、目的地拼装、发送结果判定、异常包装。
   - 延迟发送的时间换算、非正数延迟、溢出场景。
   - 异步发送回调中的成功、非 `SEND_OK`、空结果和异常回调分支。
   - `GXLocalRocketMQConfigProperties` 与 `GXNacosRocketMQConfigProperties` 的条件装配和配置来源切换。
   - `GXRocketMQMessageReqDto` 的构造逻辑、JSON 序列化和关键字段默认值。
4. 涉及配置来源、条件装配或启动期行为的修改，不能只写纯单测，必须至少补一个 Spring Boot 上下文启动测试验证真实装配结果。
5. 模块级最小验证命令为 `mvn -pl leaf-base-rocketmq test`。

## 5. 变更前检查清单

1. 是否影响 `GXSendRocketMQService` 的对外契约或调用方式。
2. 是否影响消息目的地的拼装规则：`topic`、空 `tag`、`topic:tag`。
3. 是否影响 `messageKey` 头信息写入规则。
4. 是否影响延迟发送的时间计算和异常分支。
5. 是否引入了非 ASCII 日志文本。
6. 是否进行了不必要的方法或类抽取。
7. 是否删除了冗余注释，并为复杂逻辑补齐了必要的 Javadoc 或示例。
8. 是否补充或更新了测试，并覆盖本次改动风险点。

## 6. AGENTS.md 自动触发更新时机

出现以下任一情况时，必须在同一 PR 或提交中同步更新本文件：

1. 模块职责边界变化，例如新增消费、事务消息、重试补偿、监听注册等核心能力。
2. 目录结构变化，例如新增关键包、迁移核心类、删除关键组件。
3. 对外契约变化，例如 `GXSendRocketMQService` 方法签名、异常语义、参数模型字段发生变化。
4. 消息发送语义变化，例如目的地拼装、发送结果判定、异常包装、延迟时间换算规则变化。
5. 配置装配策略变化，例如本地/Nacos 配置来源、条件注解、默认值或配置文件命名变化。
6. 测试策略变化，例如新增必须遵守的 Spring Boot 集成测试形态，或调整模块测试基线。
7. 团队新增了需要长期遵守且可复用的编码、日志、测试、文档或兼容性规则。

## 7. 提交说明建议

1. 涉及发送语义、异常语义、配置来源切换的改动，提交说明中必须写清行为变化和兼容性影响。
2. 涉及延迟发送、异步回调或参数校验的改动，提交说明中应说明新增测试覆盖了哪些关键路径。
3. 提交前确认新增或修改的日志均为 ASCII。
4. 提交前确认测试已覆盖改动点；如果暂时无法补测，需要在提交说明中明确风险和缺口。
