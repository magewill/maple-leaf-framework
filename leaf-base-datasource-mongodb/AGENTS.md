# AGENTS.md - leaf-base-datasource-mongodb

本文档用于指导 `leaf-base-datasource-mongodb` Maven 模块的后续开发、测试与评审。所有修改都必须优先保持模块边界、现有装配方式、对外接口规范和生产环境行为稳定。

## 1. 模块定位

`leaf-base-datasource-mongodb` 是 Maple Leaf Framework 中负责 MongoDB 基础设施接入的模块，核心职责包括：

1. 基于 `mongodb.datasource.*` 配置动态注册多个 `MongoClient`、`MongoDatabaseFactory`、`MongoTemplate`。
2. 兼容本地配置与 Nacos 配置场景，并自动选择对应的动态配置来源。
3. 提供动态主数据源路由能力，使标准 Mongo 注入点指向当前激活的数据源。
4. 通过 `GXMongoTemplateContext` 提供线程内、可嵌套的 `MongoTemplate` 上下文切换与快照恢复能力。
5. 提供 MongoDB Repository/Service 抽象，统一查询条件、分页、字段更新、软删除和上下文透传等通用能力。

本模块不承载具体业务建模，不实现业务流程，也不应引入与 MongoDB 基础设施无关的应用层逻辑。

## 2. 模块边界

1. 每次修改都只能发生在当前 Maven 模块内，不能顺手修改其他模块。
2. 如果需求天然跨模块，先停止修改并重新确认范围，不通过改其他模块来规避当前模块的问题。
3. 现有代码已在生产环境使用，不得随意变更公共方法签名、配置结构、异常语义、默认行为或对外接口规范。
4. 所有改动都必须在确保原有功能正确性的前提下完成；修改既有逻辑时，不得破坏已验证行为、兼容性和正确性。
5. 作为基础框架模块，性能和线程安全性属于高优先级约束；涉及上下文切换、动态路由、Bean 注册、并发访问的改动必须先评估性能回退和并发风险。

## 3. 强制行为约束

1. `GXMongoBeanDefinitionRegistryPostProcessor` 必须继续保证“有且仅有一个 primary 数据源”；缺失或重复 primary 时必须快速失败。
2. 标准 Spring Mongo 注入点 `mongoClient`、`mongoDatabaseFactory`、`mongoTemplate`、`mongoOperations` 必须继续可用，并指向动态主数据源。
3. `GXDynamicMongoDatabaseFactory` 必须根据 `GXMongoTemplateContext` 决定目标 `MongoDatabaseFactory`，不能退化为固定单数据源实现。
4. `GXMongoTemplateContext` 必须保持栈语义，`push` 与 `pop` 必须成对使用，禁止改成覆盖式单值上下文。
5. 上下文快照恢复逻辑必须保证在线程池、虚拟线程、异常分支下不会泄漏旧的 `MongoTemplate` 名称。
6. 同一个 `ClientSession` 绑定到某个数据源后，必须继续阻止在相同 session 中切换到其他数据源。
7. `GXMongoRepository` 中字段名规范化规则必须保持兼容：`id -> _id`，驼峰字段默认转下划线。
8. `GXMongoRepository` 与 `GXMongoServiceImpl` 当前对空条件的保护不能弱化；涉及更新、删除、存在性校验的操作必须继续保留非空条件约束。
9. 当前明确不支持的能力，例如 union 查询、union 分页、直接调用 mapper 方法，必须继续显式抛出异常，除非本模块明确新增对应能力并补齐测试。
10. 所有 log 日志内容必须使用 ASCII 字符。新增或修改日志时，日志消息、占位文本、固定字符串中禁止出现非 ASCII 字符。
11. 涉及敏感信息的日志必须保持克制，禁止明文输出 URI、用户名、密码、认证库等敏感配置。
12. 在线程池与虚拟线程都能满足需求，且不会破坏现有上下文传播和资源管理语义时，优先使用虚拟线程。

## 4. 代码演进规则

1. 优先沿用现有抽象层级、包结构和命名方式，避免仅为局部改动引入新的基础设施层、helper 层或包装器。
2. 不要随便将已存在的代码抽取成单独方法或类；只有当抽取后的方法或类能被两个以上地方复用，并且确实提升可维护性时，才允许抽取。
3. 修改 Repository/Service 通用能力时，优先在 `GXMongoRepository` 或 `GXMongoServiceImpl` 内完成，不要把通用逻辑散落到下游业务模块。
4. 新增保留字、默认 Bean 名、别名替换逻辑时，必须同步评估是否会破坏 Spring 默认装配。
5. 新增配置项时，必须提供清晰的默认行为或失败语义，不能让启动流程依赖隐式空值。
6. 与连接串、用户名、密码、认证库相关的处理，必须保持现有解码兼容性，不得破坏现有配置习惯。
7. 涉及公共接口、抽象基类、配置属性、上下文切换入口的修改，默认按兼容性变更处理；没有明确收益和充分验证时，不做破坏性调整。
8. 涉及并发能力时，优先选择简单、可验证、线程安全的实现。
9. 任何与多数据源、动态路由、统一数据访问抽象相关的设计，都应与框架整体数据源切换语义、命名习惯和扩展方式保持一致。

## 5. 注释与 Javadoc 规范

1. 删除方法、类、变量上的冗余注释；如果注释只是复述命名本身，应直接移除。
2. 清理 Javadoc 中的冗余信息，只保留必要文档。
3. 对复杂方法、复杂类、对外扩展点或容易误用的能力，应适当补充 Javadoc。
4. 如果某个 API 使用方式较复杂，可以在 Javadoc 中补充简短使用示例，帮助使用者理解适用场景、关键参数和行为边界。
5. Javadoc 不应承诺未测试、未实现或不稳定的行为。

## 6. 测试要求

1. 严格遵循测试驱动最佳实践：先明确失败场景和期望行为，再实现或调整代码，最后用测试验证回归。
2. 涉及到改动的点，都要先查看现有测试用例是否完整；如果现有测试没有覆盖改动影响面，必须同步补充后再提交。
3. 测试用例要覆盖正常路径、边界条件、异常路径和回归风险，不能只验证 happy path。
4. 如果功能必须在 Spring Boot 应用真实启动后才能验证，测试就应模拟真实 Spring Boot 应用启动后的状态，例如使用 `@SpringBootTest`、`ApplicationContextRunner` 或其他容器级装配测试手段，而不是只做脱离容器的伪单元测试。
5. 涉及自动配置、Bean 注册、条件装配、配置绑定的改动，优先补 Spring 容器级测试。
6. 修改动态数据源注册逻辑时，至少覆盖 primary 数据源缺失、重复、命名冲突、标准注入点与别名装配、多个 `MongoTemplate` 同时存在时的查找与切换。
7. 修改 `GXMongoTemplateContext` 或上下文透传逻辑时，至少覆盖嵌套 `push/pop`、snapshot capture/replace、异常恢复、线程池或虚拟线程中的上下文不泄漏。
8. 修改 `GXDynamicMongoDatabaseFactory` 时，至少覆盖默认工厂选择、基于上下文的数据源切换、session 绑定后禁止跨数据源切换。
9. 修改 `GXMongoRepository` 或 `GXMongoServiceImpl` 时，至少覆盖字段名转换、`_id` 映射、条件构造、操作符兼容、空条件保护、分页、单字段查询、更新、删除、复制等行为。
10. 测试评审重点是覆盖范围是否与改动风险匹配，而不仅是测试是否通过。

## 7. 变更前检查清单

每次修改前后都应检查以下问题：

1. 是否影响 `mongodb.datasource.*` 配置结构、默认值或兼容性。
2. 是否影响 primary 数据源判定、标准注入点别名或 Bean 名保留规则。
3. 是否影响 `GXMongoTemplateContext` 的栈恢复、快照恢复或跨线程透传。
4. 是否影响 `GXDynamicMongoDatabaseFactory` 的动态路由和 session 绑定约束。
5. 是否影响 `id`/`_id` 映射、字段驼峰转下划线规则或条件操作符兼容性。
6. 是否引入新的日志文案，且这些日志文案是否全部为 ASCII。
7. 是否影响对外接口规范、公共方法签名、配置结构、默认行为或异常语义。
8. 是否已经确认改动仅限当前 Maven 模块。
9. 是否已经从性能和线程安全角度评估风险，尤其是并发上下文、动态路由和跨线程执行场景。
10. 如果改动涉及并发执行方案，是否确认虚拟线程可用且更合适；如未采用，是否有明确原因。
11. 是否删除了冗余注释，并为新增复杂逻辑补充了必要 Javadoc 或使用示例。
12. 是否已经检查并补齐相关测试用例。
13. 是否确认修改后的实现仍然保持原有功能正确性，没有引入行为回归。

## 8. AGENTS.md 自动更新时机

出现以下任一情况时，应同步更新本文件：

1. 模块职责边界发生变化，例如从“仅提供 MongoDB 基础设施”扩展到新的能力域。
2. 动态数据源装配方式、默认 Bean 名、保留字、别名策略或 primary 规则发生变化。
3. `GXMongoTemplateContext` 的上下文传播模型、线程模型、栈语义或恢复语义发生变化。
4. `GXDynamicMongoDatabaseFactory` 的路由规则、session 约束或事务相关行为发生变化。
5. `GXMongoRepository` 或 `GXMongoServiceImpl` 的公共行为、异常语义、字段映射规则、查询能力边界发生变化。
6. 测试策略发生变化，例如新增必须遵守的集成测试方式、测试基线或覆盖要求。
7. 对外接口兼容性策略、性能基线、线程模型偏好、线程安全要求或“正确性不回归”约束发生变化。
8. 团队新增会持续影响后续开发的编码约束、注释规范、日志规范或提交规范。
9. 模块关键依赖、跨模块约定或启动装配方式发生重要变化。

## 9. 提交与评审建议

1. 涉及配置绑定、动态注册、上下文切换或统一查询行为的修改，PR 描述中应明确说明行为变化、兼容性影响和测试覆盖。
2. 涉及日志调整时，提交前再次检查日志文本是否全部为 ASCII，并确认没有暴露敏感配置。
3. 涉及测试调整时，说明新增测试覆盖了哪些风险，而不是只说明“测试通过”。
4. 如果改动触发本文第 8 节中的任一条件，应将 `AGENTS.md` 更新与功能改动一并提交。
