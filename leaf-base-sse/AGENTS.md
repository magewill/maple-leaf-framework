# AGENTS.md - leaf-base-sse

本文档用于指导 `leaf-base-sse` 模块的后续迭代开发。修改本模块时，优先保证 SSE 连接生命周期管理、消息推送语义、连接清理策略和对外服务契约的稳定性。现有代码已经在生产环境使用，任何变更都必须在保持原有功能正确性的前提下进行，避免与当前职责无关的重构。

## 通用硬性规则

1. 每次修改只能触碰当前 Maven 模块；确需跨模块时，先说明触发原因、受影响模块、替代方案和最小改动集合。
2. 现有代码已经在生产环境使用，不得随意更改对外接口规范、配置语义、默认行为、异常语义或序列化契约；必须变更时，同步补充兼容说明、迁移路径和回归测试。
3. 在确保原有功能正确的前提下完善实现；修改既有逻辑前，先用测试锁定当前成功、失败、空值、边界和回归路径。
4. 基础框架代码必须优先审查性能、线程安全、资源释放和并发可见性；线程池与虚拟线程都能满足需求时，优先使用虚拟线程。
5. 空值处理必须支持 JSpecify 规范：新增或修改 API、DTO、配置属性、回调、集合元素和异步结果时，明确 `@NullMarked`、`@Nullable` 或等价约束，让空值语义可被 IDE、编译检查和测试验证。
6. 严格遵循测试驱动最佳实践：先写或调整能暴露问题的测试，再实现最小代码变更，最后运行模块级验证命令。
7. 涉及改动的点都要检查测试用例是否完整；覆盖不足时补齐成功、失败、异常、空值、边界和回归场景。
8. 功能只有在 Spring Boot 应用运行后才能验证时，使用 `@SpringBootTest` 或等价方式模拟真实启动后的 Bean 装配、条件配置、AOP、监听器、异步流程和配置绑定。
9. 修改线程安全或性能相关代码时，必须补充严格测试；覆盖并发访问、重复执行、超时、取消、资源释放和关键指标，无法自动化时在提交说明写清手工压测命令、样本规模和观察指标。
10. 所有 `log` 日志内容必须使用 ASCII 字符，避免不同运行环境、终端编码或日志采集链路出现乱码。
11. 不要随便把已存在代码抽取成单独方法或类；只有抽取后的逻辑至少被两个位置复用，或能显著降低复杂度且不破坏语义时，才允许抽取。
12. 删除方法、类、变量上的冗余注释；清理 Javadoc 中重复、空泛或仅复述签名的信息，只保留语义说明、边界条件、异常约定等必要内容。
13. 复杂方法、复杂类、公共扩展点或使用方式不直观的能力，应补充必要 Javadoc；使用门槛较高时，给出简短使用示例。
14. 精准命令胜过陈词滥调：直接给出 `mvn -pl 当前模块 test`、`rg "类名|方法名" 当前模块/src/test` 这类具体步骤，避免“确保代码质量”“提升项目可维护性”等抽象套话。
15. 控制 `AGENTS.md` 长度与结构，建议保持在 200 行以内；规范继续增多时，在子目录创建领域指南，本文件只保留入口链接和必须遵守的红线。
16. 持续优化迭代：`AGENTS.md` 是动态文档；当 Agent 的实际输出与预期目标出现偏差时，把偏差改写成下一次可执行、可检查的规则。

## 1. 模块定位

`leaf-base-sse` 是 Maple Leaf Framework 中提供 Server-Sent Events 基础能力的模块，当前职责包括：

1. 提供 `GXSseEmitterService` 作为对外统一服务入口，负责 SSE 连接创建、查询、关闭、单播和广播。
2. 提供 `GXSseEmitterServiceImpl` 作为默认实现，维护基于 `ConcurrentHashMap` 的客户端连接缓存。
3. 在连接创建时注册 completion、timeout、error 回调，并在连接失效后清理缓存。
4. 支持服务端向单个客户端或全部客户端推送消息，消息体通过 `GXSseMessageInnerReqDto` 统一构造。
5. 支持基础的消息拆分、心跳探测、发送失败重试、指数退避和模块销毁时的资源释放。

当前模块不承载以下职责：

1. 不负责提供 Controller、鉴权、权限校验、租户隔离或业务级消息编排。
2. 不负责浏览器端 SSE 客户端封装、前端协议适配或 WebSocket 回退机制。
3. 不负责分布式节点间连接同步、跨实例广播或持久化消息存储。

## 2. 目录职责

1. `service`：SSE 服务契约定义，对外暴露稳定接口。
2. `service/impl`：连接缓存、回调注册、发送重试、心跳和资源清理等核心实现。
3. `dto`：SSE 内部消息 DTO，承载事件名、消息 ID、重连时间和数据负载。
4. `src/test`：测试目录。当前模块已建立 JUnit 5 与 Spring Boot 启动测试基线，后续功能改动必须同步补齐。

## 3. 强制开发规则

1. 所有 `log` 日志中的内容都必须使用 ASCII 字符，禁止新增或保留非 ASCII 日志文本。
2. 涉及改动的点，都要同步查看测试用例是否完整覆盖；覆盖不足时必须补充测试。
3. 每次修改都只能修改 `leaf-base-sse` 当前 Maven 模块内的文件，不得修改其它模块。
4. 现有代码已经在生产环境使用，不得随意更改对外接口规范、默认行为、异常传播语义或调用方可见的数据格式。
5. 在确保原有功能正确性的前提下进行完善；修改已经存在的逻辑时，不得改变现有逻辑的正确性。
6. 本模块作为基础框架能力，性能、并发正确性和线程安全性非常重要；涉及缓存、连接生命周期、异步发送、重试、回调或销毁逻辑时必须优先评估这些影响。
7. 在线程池与虚拟线程都能满足需求的场景中，优先使用虚拟线程；如选择线程池，必须说明复用、限流、上下文传播或兼容性方面的必要性。
8. 严格遵循测试驱动最佳实践。新增功能或修复缺陷时，优先通过测试描述预期行为，再进行实现或修复。
9. 不要随便将已存在的代码抽取成单独的方法或者类；只有当抽取后的逻辑可以被两个及以上位置复用，或能显著降低复杂度且不破坏可读性时，才允许抽取。
10. 将方法、类、变量上的冗余注释去掉，避免注释重复描述代码字面含义。
11. 清理 Javadoc 中的冗余信息，只保留必要文档；对复杂的方法、复杂的类、对外扩展点适当补充 Javadoc，必要时加入简短使用示例，便于后续使用者参考。
12. 修改 `GXSseEmitterService` 的公共方法签名、参数语义、返回语义或异常语义前，必须先评估兼容性影响。
13. 修改连接缓存、超时下限、心跳策略、发送失败重试次数、退避策略或默认事件名时，必须确认不会破坏现有调用方预期。
14. 修改 `GXSseMessageInnerReqDto` 字段、默认值或构造方式时，必须确认消息 ID、事件名、重连时间和数据负载的兼容性仍然成立。
15. 修改连接关闭、异常回调或销毁逻辑时，必须保证缓存清理路径完整，避免连接泄漏或重复关闭导致的副作用。

## 4. 测试要求

1. 任意功能改动前，都要先检查当前是否存在对应测试，以及这些测试是否覆盖成功路径、失败路径、异常路径和边界条件。
2. 严格遵循测试驱动最佳实践；新增功能或修复缺陷时，应先补充能暴露目标行为的测试，再编写或调整实现。
3. 测试用例要覆盖全面，至少包括以下风险点：
   - `createSseConnect` 的客户端 ID 为空场景、最小超时保护、旧连接替换、首次握手事件发送失败。
   - `sendMessageToOneClient` 的空参数、连接不存在、拆分发送、普通发送、发送失败重试。
   - `sendMessageToAllClient` 的空连接集合、空消息、广播到多个连接、单个连接发送失败后的清理。
   - `splitMessage` 的空消息、超短消息、超长消息、长度边界和拆分结果完整性。
   - `closeConnect`、`sendHeartbeat`、`closeConnections`、`destroy` 的资源释放与缓存变更。
4. 如果某项功能只有在 Spring Boot 应用真正启动后才能验证，例如 `@Service` 装配、Bean 生命周期回调、`@PreDestroy`、`SseEmitter` 与 Spring MVC 容器协作行为，那么测试必须使用接近真实运行方式的 Spring Boot 集成测试，例如 `@SpringBootTest`，不能只做纯单元测试。
5. 纯工具型逻辑可以使用单元测试，但涉及 Spring 容器、生命周期、自动装配或 Web 层协作的行为，必须至少补一个真实 Spring Boot 启动场景测试。
6. 涉及并发、缓存、连接清理、重试、异步发送或虚拟线程选择的改动，测试必须覆盖线程安全、资源释放和失败恢复场景。
7. 当前模块已建立最小可运行测试骨架。后续修改本模块代码时，必须继续补齐与改动点匹配的单元测试或 Spring Boot 集成测试。
8. 最小验证命令为 `mvn -pl leaf-base-sse test`。

## 5. 变更前检查清单

1. 是否影响 `GXSseEmitterService` 的对外契约或调用方式。
2. 是否影响连接缓存键的生成、覆盖或回收语义。
3. 是否影响发送事件的 `id`、`name`、`comment`、`reconnectTimeMillis` 或 `data` 格式。
4. 是否影响心跳、重试、退避、超时和销毁时的资源释放行为。
5. 是否引入了非 ASCII 日志内容。
6. 是否进行了没有复用价值的方法或类抽取。
7. 是否删除了冗余注释和冗余 Javadoc，并为复杂逻辑补足了必要的 Javadoc 或示例。
8. 是否检查并补齐了与改动点匹配的测试。
9. 是否只修改了 `leaf-base-sse` 当前 Maven 模块内的文件。
10. 是否保持生产环境已使用的对外接口规范、默认行为和异常传播语义稳定。
11. 是否评估了性能、并发正确性和线程安全性影响。
12. 是否在适合的异步或并发场景中优先考虑了虚拟线程。
13. 是否遵循测试驱动最佳实践，先用测试描述目标行为再调整实现。
