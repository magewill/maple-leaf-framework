# AGENTS.md - leaf-base-sse

本文档用于指导 `leaf-base-sse` 模块的后续迭代开发。修改本模块时，优先保证 SSE 连接生命周期管理、消息推送语义、连接清理策略和对外服务契约的稳定性，避免与当前职责无关的重构。

## 1. 模块定位

`leaf-base-sse` 是 Maple Leaf Framework 中提供 Server-Sent Events 基础能力的模块，当前职责包括：

1. 提供 `GXSseEmitterService` 作为对外统一服务入口，负责 SSE 连接创建、查询、关闭、单播和广播。
2. 提供 `GXSseEmitterServiceImpl` 作为默认实现，维护基于 `ConcurrentHashMap` 的客户端连接缓存。
3. 在连接创建时注册 completion、timeout、error 回调，并在连接失效后清理缓存。
4. 支持服务端向单个客户端或全部客户端推送消息，消息体通过 `GXSseMessageInnerReqDto` 统一构造。
5. 支持基础的消息拆分、心跳探测、发送失败重试、指数退避和模块销毁时的资源释放。

当前模块不承载以下职责：

1. 不负责提供 Controller、鉴权、权限校验、租户隔离或业务级消息编排。
2. 不负责浏览器端 SSE 客户端封装、前端协议适配或 WebSocket 回退机制。
3. 不负责分布式节点间连接同步、跨实例广播或持久化消息存储。

## 2. 目录职责

1. `service`：SSE 服务契约定义，对外暴露稳定接口。
2. `service/impl`：连接缓存、回调注册、发送重试、心跳和资源清理等核心实现。
3. `dto`：SSE 内部消息 DTO，承载事件名、消息 ID、重连时间和数据负载。
4. `src/test`：测试目录。当前模块尚未建立测试基线，后续功能改动必须同步补齐。

## 3. 强制开发规则

1. 所有 `log` 日志中的内容都必须使用 ASCII 字符，禁止新增或保留非 ASCII 日志文本。
2. 涉及改动的点，都要同步查看测试用例是否完整覆盖；覆盖不足时必须补充测试。
3. 不要随便将已存在的代码抽取成单独的方法或者类；只有当抽取后的逻辑可以被两个及以上位置复用，或能显著降低复杂度且不破坏可读性时，才允许抽取。
4. 将方法、类、变量上的冗余注释去掉，避免注释重复描述代码字面含义。
5. 对复杂的方法、复杂的类、对外扩展点适当补充 Javadoc；必要时加入简短使用示例，便于后续使用者参考。
6. 修改 `GXSseEmitterService` 的公共方法签名、参数语义、返回语义或异常语义前，必须先评估兼容性影响。
7. 修改连接缓存、超时下限、心跳策略、发送失败重试次数、退避策略或默认事件名时，必须确认不会破坏现有调用方预期。
8. 修改 `GXSseMessageInnerReqDto` 字段、默认值或构造方式时，必须确认消息 ID、事件名、重连时间和数据负载的兼容性仍然成立。
9. 修改连接关闭、异常回调或销毁逻辑时，必须保证缓存清理路径完整，避免连接泄漏或重复关闭导致的副作用。

## 4. 测试要求

1. 任意功能改动前，都要先检查当前是否存在对应测试，以及这些测试是否覆盖成功路径、失败路径、异常路径和边界条件。
2. 测试用例要覆盖全面，至少包括以下风险点：
   - `createSseConnect` 的客户端 ID 为空场景、最小超时保护、旧连接替换、首次握手事件发送失败。
   - `sendMessageToOneClient` 的空参数、连接不存在、拆分发送、普通发送、发送失败重试。
   - `sendMessageToAllClient` 的空连接集合、空消息、广播到多个连接、单个连接发送失败后的清理。
   - `splitMessage` 的空消息、超短消息、超长消息、长度边界和拆分结果完整性。
   - `closeConnect`、`sendHeartbeat`、`closeConnections`、`destroy` 的资源释放与缓存变更。
3. 如果某项功能只有在 Spring Boot 应用真正启动后才能验证，例如 `@Service` 装配、Bean 生命周期回调、`@PreDestroy`、`SseEmitter` 与 Spring MVC 容器协作行为，那么测试必须使用接近真实运行方式的 Spring Boot 集成测试，例如 `@SpringBootTest`，不能只做纯单元测试。
4. 纯工具型逻辑可以使用单元测试，但涉及 Spring 容器、生命周期、自动装配或 Web 层协作的行为，必须至少补一个真实 Spring Boot 启动场景测试。
5. 当前模块还没有 `src/test` 基线。后续首次修改本模块代码时，应优先建立最小可运行测试骨架，并确保模块级测试命令可执行。
6. 最小验证命令为 `mvn -pl leaf-base-sse test`。

## 5. 变更前检查清单

1. 是否影响 `GXSseEmitterService` 的对外契约或调用方式。
2. 是否影响连接缓存键的生成、覆盖或回收语义。
3. 是否影响发送事件的 `id`、`name`、`comment`、`reconnectTimeMillis` 或 `data` 格式。
4. 是否影响心跳、重试、退避、超时和销毁时的资源释放行为。
5. 是否引入了非 ASCII 日志内容。
6. 是否进行了没有复用价值的方法或类抽取。
7. 是否删除了冗余注释，并为复杂逻辑补足了必要的 Javadoc 或示例。
8. 是否检查并补齐了与改动点匹配的测试。

## 6. AGENTS.md 自动触发更新时机

出现以下任一情况时，必须在同一个 PR 或提交中同步更新本文件：

1. 模块职责边界变化，例如新增 SSE 订阅管理、认证接入、跨节点广播、持久化消息或新的核心能力。
2. 目录结构变化，例如新增关键包、拆分实现层、引入新的配置层、删除核心类。
3. 对外契约变化，例如 `GXSseEmitterService` 方法签名、参数语义、返回值、异常语义发生变化。
4. 连接管理策略变化，例如客户端 ID 生成规则、连接缓存结构、超时策略、关闭策略、清理策略发生变化。
5. 消息模型变化，例如 `GXSseMessageInnerReqDto` 字段、默认值、事件格式、重连时间或数据结构发生变化。
6. 发送可靠性策略变化，例如心跳策略、失败重试次数、指数退避规则、异常处理路径发生变化。
7. 测试基线变化，例如新增必须遵守的 Spring Boot 集成测试要求、建立或重构模块测试骨架、最低验证命令变化。
8. 团队新增了需要长期遵守且适用于本模块的编码、日志、测试、注释或文档规则。

## 7. 提交说明建议

1. 涉及 SSE 连接行为、消息发送语义、重试策略或连接清理逻辑的改动，提交说明中应明确写清行为变化和兼容性影响。
2. 涉及日志调整的改动，提交前确认新增和修改后的日志文本全部为 ASCII。
3. 涉及消息 DTO、事件格式或连接生命周期的改动，提交说明中应写明新增或更新了哪些测试覆盖。
4. 如果理论上应补测试但暂时无法补齐，必须在提交说明中明确风险、缺口和后续计划。
