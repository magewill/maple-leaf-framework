# AGENTS.md (leaf-base-framework)

## 模块定位

`leaf-base-framework` 是 Maple Leaf Framework 的基础核心模块，负责提供跨业务复用的框架能力：

- 通用注解与 AOP，如业务日志、参数校验、耗时统计。
- Web 横切能力，如 `RequestBodyAdvice`、`ResponseBodyAdvice`、Filter、Interceptor。
- 基础 DTO、统一返回结构、状态码、异常模型。
- Caffeine / Spring Cache 基础配置、事件、上下文、MDC 透传、通用工具、DDD 基础接口。

本模块不要引入具体业务域规则、业务流程编排或业务常量。

## 缓存规范

- 缓存注解统一使用 Spring Cache：`@Cacheable`、`@CacheEvict`、`@CachePut`、`@Caching`。
- 本模块只维护 Spring Cache 所需的基础设施，如 `CaffeineCacheManager`、`CachingConfigurer` 和缓存配置属性。
- 不再新增 Leaf 自定义缓存注解或对应切面，避免与 Spring Boot 缓存机制重复。
- 需要分布式缓存时，优先通过 Spring Cache 的 `CacheManager` 扩展或现有 `GXBaseCacheService` 实现接入。

## 目录职责

- `annotation`：框架通用注解定义，不包含自定义缓存注解。
- `aspect`：通用横切逻辑，如业务日志、参数校验、耗时统计。
- `config`：框架配置，如异步、CORS、Filter、缓存、Web 适配。
- `service` 和 `service.impl`：可替换的框架服务 SPI 与默认实现。
- `web`、`filter`、`handler`：Web 层横切增强与请求处理辅助。
- `dto`、`api.dto`、`code`、`exception`：协议对象、状态码、异常模型。
- `event`：事件总线与事件处理基础设施。
- `util`、`wrapper`：通用工具与 MDC 包装器。
- `ddd`：DDD 基础抽象。

## 开发约束

- 对外注解、DTO 字段、公共方法签名默认视为稳定契约，修改前先评估影响面。
- 现有代码已经在生产环境使用，不得随意修改对外接口规范、默认行为、异常语义或序列化协议；确需调整时必须评估兼容性并补充迁移说明。
- 完善已有功能时，必须以确保原有功能正确性为前提；修改既有逻辑时，不得破坏现有正确行为，修复范围应尽量收敛并补充对应回归测试。
- 本模块作为基础框架，代码性能、线程安全性和资源释放路径都属于核心质量要求；公共工具、缓存、上下文透传、反射和转换逻辑修改时必须重点审查热点路径开销与并发安全。
- 在线程池与虚拟线程都能满足需求的场景中，优先使用虚拟线程；只有需要固定线程资源、复用线程本地状态、绑定专用调度器或受第三方组件限制时，才优先选择传统线程池。
- 每次修改涉及到的行为变更，都必须补齐或更新测试用例，并保证覆盖完整的成功、异常、边界和回归场景。
- 新增能力优先复用 Spring Boot / Spring Framework 标准机制。
- 新增框架能力前，必须先判断是否与 Spring Boot 本身已经提供的功能重复；若重复，优先使用 Spring Boot 原生能力或基于其扩展点增强。
- 不要随意把已存在代码抽取成单独方法或类；只有当抽取后的逻辑至少能被两个以上位置复用，或能显著降低复杂度时，才进行抽取。
- 配置类保持可读、可覆盖、可观测，避免硬编码环境值。
- 涉及请求上下文的逻辑必须考虑异步线程和非 Web 调用。
- 涉及 ThreadLocal / MDC 的代码必须有清理路径。
- 所有 `log` 日志内容必须使用 ASCII 字符，避免不同运行环境、终端编码或日志采集链路出现乱码。
- 禁止提交真实密钥、令牌、生产地址或密码。
- 将方法、类、变量上的冗余注释去掉，避免注释重复描述代码字面含义。
- 在复杂的方法、类和对外扩展点上适当补充 Javadoc；必要时增加简短使用示例，便于后续使用者参考。

## 测试要求

- 涉及代码改动时，必须同步查看相关测试用例是否完整覆盖了改动点；若覆盖不足，应补充或更新测试。
- 修改 `aspect`、`web.advice`、`filter`、`handler`、`wrapper.mdc` 时，必须重点检查成功路径、异常路径、空值路径和框架扩展点行为。
- 测试用例必须覆盖全面；如果功能依赖 Spring Boot 应用启动后的容器、自动配置、AOP、Web、异步或事件机制，测试应使用接近真实的
  Spring Boot 应用上下文启动方式验证。
- 修改公共 DTO 或协议对象时，至少验证序列化、反序列化或核心字段兼容性。
- 最小验证命令：`mvn -pl leaf-base-framework test`。

## 并发与线程工具约束

- 新增或修改线程池、`CompletableFuture`、异步事件、MDC/TraceId 透传逻辑时，必须覆盖正常完成、异常完成、超时、取消和中断恢复路径。
- 在线程池线程中写入 MDC 或 ThreadLocal 后，必须在 `finally` 中恢复调用前上下文；没有上游上下文时必须显式 `clear`
  ，避免复用线程携带脏数据。
- `CompletableFuture.cancel(true)` 默认不保证中断底层任务；如果 API 语义要求取消运行中的任务，需要将取消动作传递到实际提交给
  `ExecutorService` 的 `Future`。
- 不要向 `ConcurrentHashMap`、`ConcurrentMap` 默认实现写入 `null` 值；聚合结果需要区分失败、空结果和缺失时，应使用显式哨兵值或专门结果对象。
- 等待多个异步任务时，超时或异常后要记录已完成/未完成数量，并对未完成任务执行取消；捕获 `InterruptedException` 后必须恢复线程中断标记。
- 接收 `Future` / `CompletableFuture` 集合的公共方法必须显式拒绝 `null` 集合、空集合和集合内的 `null` 元素，避免在等待阶段暴露不清晰的
  NPE。
- 模块级共享线程池属于 JVM 生命周期资源；除 JVM 关闭流程或专门生命周期测试外，不要在普通单元测试、请求流程或业务流程中调用关闭方法。
- 并发工具测试需要避免依赖全局统计初始值；可验证统计格式、状态变化方向或任务结果，不要假定测试 JVM 中没有其他任务运行。

## SpEL 工具约束

- SpEL 表达式缓存的 key 应尽量保持稳定，不要把用户实参直接拼进表达式文本；方法实参优先通过 `EvaluationContext` 变量绑定。
- 拼装 SpEL 方法调用时必须避免字符串转义、同类型参数变量名冲突和对象参数泄漏；变量名应使用调用内稳定的索引形式，例如 `#p0`、
  `#p1`。
- 公共方法调用工具必须支持无参方法；`null` 参数类型数组按空数组处理，`null` 实参数组按空实参数组处理。
- 修改表达式缓存、方法缓存或上下文构造器时，必须考虑并发调用、缓存上限、异常路径以及 Spring `StandardEvaluationContext`
  非共享使用原则。

## AGENTS.md 更新时机

以下场景必须主动检查并更新 `AGENTS.md`：

- 删除、替换或新增模块级框架能力时。
- 发现已有规则与 Spring Boot / Spring Framework 原生机制重复或冲突时。
- 调整模块边界、目录职责、公共扩展点或稳定契约时。
- 修复的问题暴露出可复用的开发约束、红线或测试要求时。
- 引入新的基础设施依赖、跨模块约定或默认开发流程时。

## 注释与文档规则

- 删除方法、类、变量上的冗余注释；能够通过命名、类型和局部代码直接理解的内容，不再添加或保留重复解释。
- 对复杂的方法、类、扩展点或公共工具能力，适当补充 Javadoc 文档；必要时在 Javadoc 中加入简短使用示例，方便后续使用者理解调用方式、边界条件和典型场景。
