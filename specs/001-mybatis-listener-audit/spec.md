**Feature Branch**: `specs/001-mybatis-listener-audit`（本次未通过 git 扩展创建分支）

**Created**: 2026-10-21

**Status**: Draft

**Input**: User description: "请审查 leaf-base-datasource 模块下监听 MyBatisPlus 操作的切面功能，它们的实现功能正确吗？满足线程安全与高性能的要求吗?"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 监听回调与真实落库结果严格一致 (Priority: P1)

业务开发者依赖"数据变更监听"驱动审计留痕、缓存失效与下游推送。他希望：只要写操作成功落库，就能拿到恰好一次、内容准确的回调；写操作失败或被回滚时，不会收到任何"已提交"语义的回调。

**Why this priority**: 错误或重复的事件比没有事件更危险——它会污染审计数据、误删缓存、向外部系统推送不存在的变更。正确性是本能力存在的前提。

**Independent Test**: 在单模块内构造"成功 / 返回 0 行 / 抛异常 / 事务回滚 / 无事务"五类写操作，逐项断言回调次数、回调载荷与数据库最终状态是否一致。

**Acceptance Scenarios**:

1. **Given** 写操作返回 0 行或执行失败，**When** 调用返回，**Then** 不产生任何监听回调。
2. **Given** 写操作处于事务中且最终回滚，**When** 事务结束，**Then** 声明为"提交后执行"的回调不发生，事务内的回调不得让调用方误以为数据已提交。
3. **Given** 同一数据访问接口同时存在方法级与类型级监听声明，**When** 执行该方法，**Then** 按方法级声明投递且仅投递一次。
4. **Given** 数据访问接口从父接口继承了监听声明，**When** 执行继承来的方法，**Then** 仍能命中该声明，且不因接口层级而重复投递。
5. **Given** 更新或删除的筛选条件可被无损还原，**When** 回调触发，**Then** 监听方能读到条件字段与取值；**Given** 条件含 `OR`、子查询、函数或原始条件导致无法无损还原，**Then** 必须附带原始条件文本，且不得伪造或错位填充字段值。
6. **Given** 该写操作没有任何监听声明，**When** 执行，**Then** 不构造事件、不产生可测量的额外开销。

---

### User Story 2 - 并发与异步下的隔离、不丢失、不串扰 (Priority: P2)

业务开发者希望在高并发写入与异步回调混跑时，每个回调看到的都是自己那次操作的数据与上下文（数据源、数据权限、追踪信息），监听方出问题不会污染业务结果，也不会把上下文带到下一个任务。

**Why this priority**: 监听回调常用于跨库校验与权限相关处理。上下文串扰会导致"查错库、越权读"；静默丢事件会导致数据不一致且难以追查。

**Independent Test**: 以并发线程 + 有界队列 + 人为阻塞回调的方式压测，校验事件归属、上下文取值、异常隔离与拒绝行为。

**Acceptance Scenarios**:

1. **Given** 200 个并发写操作各自声明了不同监听器，**When** 全部完成，**Then** 每个回调只收到自己那次操作的数据，无错配、无重复。
2. **Given** 异步回调在池化线程中执行，**When** 回调内部读取数据源与数据权限上下文，**Then** 取值与提交任务的调用方一致；**When** 任务结束，**Then** 上下文被清理，同一线程的下一个任务不受影响。
3. **Given** 某个监听器抛出异常，**When** 同一事件存在多个监听方，**Then** 其他监听方仍被调用，业务写操作的结果不被改变。
4. **Given** 异步队列已满，**When** 新事件到达，**Then** 以明确、可观测的方式拒绝，不在业务线程内同步执行，不阻塞写入，也不静默丢弃。
5. **Given** 应用正在关闭，**When** 仍有已接受的异步任务，**Then** 在配置的等待窗口内完成，超时后明确记录未完成任务数。

---

### User Story 3 - 写路径开销与容量可控 (Priority: P3)

框架维护者希望开启监听后，普通写操作的性能下降在可接受范围内；批量写入时不会因为载荷复制导致内存翻倍甚至溢出。

**Why this priority**: 监听是横切能力，任何写操作都会经过它。开销失控会拖慢所有业务，且难以归因到"监听"这一项。

**Independent Test**: 在无监听、同步监听、异步监听三种配置下，对单条写与批量写做基准对比，并采集分配速率与峰值内存。

**Acceptance Scenarios**:

1. **Given** 未声明任何监听，**When** 执行单条写操作，**Then** 相对无该能力的基线，额外耗时与内存分配在约定阈值内（不构造事件对象）。
2. **Given** 声明了监听，**When** 执行单条写操作，**Then** 监听引入的额外耗时（不含业务回调本身）不超过约定上限。
3. **Given** 一次批量写入 N 条记录，**When** 投递监听事件，**Then** 载荷只做一次快照，内存占用随 N 线性增长，不出现多份全量副本。
4. **Given** 同一操作命中多个监听声明，**When** 投递，**Then** 事件条件匹配不重复解析，开销随监听数量线性增长而非指数增长。

---

### User Story 4 - 可诊断、可开关、可回退 (Priority: P4)

运维与框架维护者希望：当监听被拒绝、降级或失败时，能通过日志与计数快速定位是"哪个事件、哪次操作、什么原因"；在异常情况下能一键关闭异步回调或整体监听，回到无监听基线。

**Why this priority**: 横切能力缺少可观测性时，故障只能靠猜；缺少开关时，线上问题只能靠回滚版本。

**Independent Test**: 人为制造拒绝、解析降级、监听异常三类故障，检查日志字段、计数器与开关生效后的行为。

**Acceptance Scenarios**:

1. **Given** 发生队列拒绝、条件解析降级或监听异常，**When** 故障出现，**Then** 输出结构化日志，包含事件类型、运行模式、原因与关联的操作标识。
2. **Given** 运维关闭异步回调开关，**When** 再次执行写操作，**Then** 不再产生异步任务，且行为与"仅同步监听"配置一致。
3. **Given** 运维关闭整体监听开关，**When** 执行写操作，**Then** 无事件产生，写路径回到无监听基线。
4. **Given** 运行期发生投递失败，**When** 查询投递计数，**Then** 成功、失败、拒绝、降级四类计数可区分且单调递增。

---

### Edge Cases

- 事务边界：无事务、单层事务、嵌套事务、只读事务、事务提交后又触发第二次写。
- 写操作结果：返回 0 行、返回负数、返回 `null`、抛出受检异常、抛出运行时异常。
- 批量输入：空集合、只含 `null` 元素的集合、超大集合（≥ 10 万条）、集合在投递后被调用方修改。
- 监听声明：监听器不存在、监听器类型不匹配、同一接口被多个父接口声明、方法级与类型级冲突、同一监听器被重复声明。
- 条件还原：`OR`、`AND` 与 `OR` 混用、`IN`、`BETWEEN`、`IS NULL`、子查询、函数表达式、重复字段、原始 SQL、无参数条件。
- 递归触发：监听器内部再次写库并被同一监听声明命中。
- 执行器：队列饱和、线程池初始化失败、停机中提交、虚拟线程模式与池化模式切换。
- 载荷变更：监听器修改回调载荷中的可变对象（如日期、集合）后，不影响业务对象与其他监听方。

## Requirements *(mandatory)*

### Functional Requirements

**投递正确性**

- **FR-001**: 系统 MUST 仅在写操作被判定为"生效"（返回值表示至少影响 1 行）时投递事件。
- **FR-002**: 系统 MUST 保证一次写操作对同一监听声明最多投递一次；继承关系导致的重复声明 MUST 合并为一次。
- **FR-003**: 系统 MUST 按声明区分"同步执行"与"提交后执行"两种投递模式，且一次操作只投递其声明模式对应的事件类型。
- **FR-004**: 声明为"提交后执行"的事件 MUST 在事务成功提交后投递；事务回滚时 MUST NOT 投递。
- **FR-005**: 无活动事务时，"提交后执行"事件 MUST 立即投递，且保留调用方可见的异常行为。
- **FR-006**: 事件投递 MUST NOT 改变原写操作的返回值；同步模式下的回调异常处理策略 MUST 明确且可配置，默认行为不得让已成功的写操作被静默回滚。
- **FR-007**: 系统 MUST 支持方法级监听声明优先于类型级声明，并能识别父接口与父类上的声明。

**载荷准确性**

- **FR-008**: 事件载荷 MUST 是发布时刻的不可变快照；监听方对载荷的修改 MUST NOT 影响业务对象、数据库参数或其它监听方。
- **FR-009**: 更新与删除事件 MUST 提供可还原的条件字段与取值；无法无损还原时 MUST 附带原始条件文本并明确标记为"仅原始条件"。
- **FR-010**: 条件字段与取值的对应关系 MUST NOT 依赖隐式顺序假设；无法确定对应关系时 MUST 降级而非错配。
- **FR-011**: 批量事件 MUST 保序呈现该批次的数据，且同一批次只产生一次回调。
- **FR-012**: 系统 MUST 明确声明能力覆盖边界（哪些写操作会产生事件、哪些不会），未覆盖的操作 MUST 在文档中可见。

**并发与上下文**

- **FR-013**: 监听分发组件 MUST 无共享可变状态；所有缓存 MUST 并发安全且有容量上限。
- **FR-014**: 异步回调 MUST 继承调用方的数据源上下文、数据权限上下文与追踪标识；任务结束 MUST 恢复或清理，不得跨任务残留。
- **FR-015**: 单个监听器异常 MUST NOT 阻止同一事件的其他监听器执行。
- **FR-016**: 异步任务被拒绝时 MUST 保持业务写操作成功，并产生可观测的拒绝记录。
- **FR-017**: 应用关闭时 MUST 在配置的等待窗口内完成已接受任务，并记录未完成数量。

**性能与可运维**

- **FR-018**: 无监听声明的写操作 MUST 不构造事件载荷、不进行条件解析、不产生额外线程调度。
- **FR-019**: 监听能力 MUST 提供整体开关与异步模式开关，关闭后行为与无监听基线一致。
- **FR-020**: 系统 MUST 提供成功、失败、拒绝、降级四类运行时计数，并输出包含事件类型与原因的结构化日志。

### Key Entities

- **写操作事件**：一次成功写操作的抽象；属性包括操作种类、事件类型（同步/异步）、事件名称、发生时间与载荷。
- **监听声明**：绑定在数据访问方法或接口上的配置；属性包括目标监听器、投递模式、生效范围。
- **回调载荷**：监听方消费的数据快照；属性包括实体数据、更新字段、条件字段与取值、原始条件文本、批次数据。
- **投递任务**：异步模式下排队执行的单元；属性包括载荷、继承的上下文、提交时间、执行耗时。
- **投递结果**：一次投递的结局；分为成功、失败、拒绝、降级，用于计数与告警。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在"成功 / 0 行 / 异常 / 回滚 / 无事务"五类场景矩阵中，回调次数与载荷同数据库最终状态的一致率为 100%。
- **SC-002**: 200 并发 × 7 类写操作的压测中，事件错配 0 次、重复 0 次、丢失 0 次，上下文串扰 0 次。
- **SC-003**: 未声明监听的写操作，相对移除该能力后的基线，P95 额外耗时不超过 2%，且事件对象分配次数为 0。
- **SC-004**: 声明监听的单条写操作，监听引入的额外开销（不含业务回调耗时）P95 不超过 1 毫秒。
- **SC-005**: 单次批量写入 1 万条时，监听载荷的峰值内存不超过实体数据本身大小的 2 倍。
- **SC-006**: 队列饱和场景下，业务写操作成功率为 100%，被拒绝事件 100% 可通过日志与计数定位。
- **SC-007**: 关闭开关后，写操作的行为与性能回退到无监听基线（差异在测量误差内）。
- **SC-008**: 条件无法无损还原的场景中，100% 附带原始条件文本，且 0 例出现字段与取值错配。
- **SC-009**: 现有依赖方升级后无需修改业务代码即可通过编译与既有测试，公共声明与语义保持向后兼容。

## Assumptions

- 审查范围限定为 `leaf-base-datasource` 中与"写操作监听"直接相关的组件：保存、更新、条件更新字段、软删除、物理删除、批量保存六类切面，同步/异步两个监听分发器，异步执行器配置，以及监听声明与事件定义。数据源切换与数据权限切面仅在影响监听链路时纳入。
- 现有的"同步在业务线程执行、异步在提交后执行"语义属于已发布契约；除缺陷修复外不改变默认行为，需要改变语义时以显式开关提供并默认保持兼容。
- 该能力定位为"至多一次"的内存内投递，不要求持久化消息或事务性发件箱；极端进程崩溃导致的丢失不在本次目标内。
- 事件投递由注解声明触发；未声明的写操作视为不需要事件，不承担额外开销。
- 允许新增回归测试、并发测试与基准测试；不引入新的第三方运行时依赖。
- 兼容性以"现有调用方代码与配置无需修改"为判定标准；内部实现可调整。
- 团队可提供一台具备多核与可运行本地数据库/中间件的环境用于并发与基准验证；无法自动化的验证需给出可复现命令与观察指标。

## 附录：现状审查基线（需求来源）

以下为本次审查对现有实现的结论，作为上述需求的来源与验收背景。逐条对应到功能需求，便于后续计划阶段定位。

| 关注点 | 现状观察 | 结论 | 关联需求 |
| --- | --- | --- | --- |
| 生效判定 | 仅当返回值表示影响行数 > 0 时投递 | 符合预期 | FR-001 |
| 投递去重 | 按匹配到的每个数据访问接口各投递一次，多接口继承时会发出多次 | 存在重复投递风险 | FR-002、FR-007 |
| 事务边界 | 异步声明走"提交后投递"；同步声明在业务线程内、事务尚未结束时投递 | 同步模式存在"未提交即通知"风险 | FR-003、FR-004 |
| 同步回调异常 | 异常直接向业务调用方传播，且监听方法刻意不声明事务边界 | 已成功的写操作可能被连带回滚 | FR-006 |
| 无事务场景 | "提交后投递"在无活动事务时退化为立即投递 | 符合预期 | FR-005 |
| 载荷快照 | 事件构造时深拷贝 Map/集合/数组/日期；对不可克隆对象返回原引用 | 基本符合，存在可变对象逃逸风险 | FR-008 |
| 条件还原 | 解析 SQL 片段并由缓存复用；`OR`、函数、重复字段、无参数条件降级为原始条件文本；投递前校验参数名与数量 | 基本正确，但强依赖 SQL 文本形态 | FR-009、FR-010 |
| 批量处理 | 仅拦截通用服务层的批量保存与批量新增或更新 | 覆盖不完整（自定义批量不经此路径） | FR-011、FR-012 |
| 物理删除 | 仅拦截"按条件删除"，按主键删除不产生事件（有意设计） | 能力边界需显式声明 | FR-012 |
| 线程安全 | 切面无实例状态；条件解析缓存有容量上限与过期策略；载荷为快照 | 符合预期 | FR-013 |
| 异步上下文 | 任务提交时包装数据源与数据权限上下文，并在执行后恢复 | 符合预期（依赖包装实现的 finally） | FR-014 |
| 异常隔离 | 单个监听器异常会中断该事件的后续监听器与后续声明 | 存在隔离缺陷 | FR-015 |
| 拒绝策略 | 有界队列 + 显式拒绝 + 错误日志，不在调用方执行 | 符合预期 | FR-016 |
| 优雅停机 | 等待已接受任务完成，并设置终止等待时间 | 基本符合，未完成数量缺少汇总 | FR-017 |
| 执行器配置 | 池化模式下核心/最大线程数默认取 CPU 核数；虚拟线程模式下并发上限等于最大线程数，且校验用执行器忽略开关恒为虚拟线程 | 存在容量与配置一致性问题 | FR-018、FR-019 |
| 性能特征 | 每次写操作都会构造事件并深拷贝载荷；每个事件要经过全部监听方法的条件判断 | 有明确优化空间 | FR-018、SC-005 |
| 可观测性 | 有任务开始/完成/失败/长耗时/拒绝日志，但缺少投递计数与降级计数 | 不满足运维要求 | FR-020 |
| 开关 | 具备异步线程与虚拟线程相关配置，缺少"整体监听"与"异步模式"的显式开关 | 不满足回退要求 | FR-019 |
