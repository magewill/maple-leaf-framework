## 3. 链路可靠性定性规则

| 定性 | 判定条件（必须全部满足） |
| --- | --- |
| 至少一次 | 消费失败时消息保留在 Redis（未 `ack`/未删除）；且有重投机制且重投不丢失 |
| 至多一次 | 消息移出 Redis 后仅存在于进程内存；进程异常即不可恢复 |
| 尽力投递 | 存在"捕获异常后视为成功"的路径，且无补偿或重试入口 |

**强制要求**：每条链路必须指出**决定性代码行**。示例：延迟队列链路的定性决定行是"消息移出 Redis 后写入 `inFlightMessages`（内存）"这一行，而非"有重试逻辑"——重试只在进程存活时有效，不改变定性。

## 4. 性能口径规则

- 只统计**同步阻塞的网络往返**；本地集合操作计 0。
- 批量接口（如 `drainTo`）按实现计为 1 次（已核对依赖源码为单段 Lua），不得按"条数"折算。
- 必须区分"每轮上限"与"单条成本"，两者相乘才是吞吐上界。
- 分布式锁必须标注**锁的粒度**（按 topic / 全局 / 按 key）与**持锁期间的操作数**。
- 禁止出现绝对毫秒数，除非同时给出测量环境与样本量（本次不采集，故不出现）。

## 6. 日志与可观测性判定规则（FR-013）

- "已启用但未生效"必须 warn 及以上；"类路径无该能力"允许 debug。
- 判定缺陷前必须核对：该失败路径是否有可检索日志、级别是否与后果匹配。
- 示例：`GXRedissonStreamImmediateMQ` 的 `BUSYGROUP` 以外建组失败只记 warn，随后读循环每秒报错——报告需指出"启动期失败被降级为 warn"，而非仅记录"有日志"。
