## 背景与审查结论摘要

本规格把"`leaf-base-redisson` 现有实现是否正确、是否线程安全、是否存在性能结构问题"这一审查问题，转化为可验收的交付要求。审查对象与证据来源：

1. `leaf-base-redisson` 全部 51 个生产源码文件（含各包 `package-info.java`）与 `src/main/resources/application.yml`；
2. 既有唯一测试类 `RedissonUtilityRegressionTest`（38 个用例，全部为 Mock/反射级用例，不依赖真实 Redis）；
3. 模块契约来源：`leaf-base-redisson/AGENTS.md`、`.specify/memory/constitution.md`；
4. 依赖基线：`org.redisson:redisson:4.7.0`、`redisson-spring-cache:4.7.0`、JDK 21 虚拟线程。

审查结论：

| 维度 | 结论 | 判定 |
| --- | --- | --- |
| 逻辑正确性 | 配置装配、Spring Cache 基础读写、锁/计数器参数校验路径基本可用；但**订阅缓存无法自愈**、**延迟转发退化为至多一次**、**stream 无 handler 时静默丢弃**三条链路存在"无报错但消息丢失"的风险 | 存在高风险缺陷 |
| 线程安全 | 显式共享状态以 `ConcurrentHashMap`/`volatile` 保护为主，`destroy` 路径做了二次清理；但**消费者并发度随注册顺序变化**、**静态缓存跨上下文持有旧客户端**、**in-flight 无界累积**三处缺少确定性约束 | 有并发风险，需约束 |
| 性能 | 单一消费路径的 RTT 数量与锁粒度缺乏上限约束：延迟 stream 转移为**全局单锁 + 每消息 6 次串行往返**，延迟队列转发**无背压**，锁工具**每次加解锁多 2 次往返** | 存在结构性瓶颈 |

关键证据（均可按位置复核）：

- **E-01**：`GXRedissonMQUtils.subscribe` 以 `LISTENER_REGISTRATION_CACHE.computeIfAbsent`（第 81–93 行）实现"同主题同消息类型只订阅一次"，返回已缓存 `listenerId`；缓存只在 `unsubscribe`（第 136–144 行）成功后才清理。
- **E-02**：`GXRedissonDelayMQPostProcessor` 从 Redis 队列取出消息后仅写入进程内 `inFlightMessages`（第 176–188 行）与本地有界队列，未做 Redis 侧确认或持久化。
- **E-03**：`GXRedissonDelayMQPostProcessor.processMessageAsync`（第 278–320 行）在消费者线程内直接提交 `CompletableFuture` 后立即返回，`consumeMessages`（第 250–276 行）不等待结果；`MAX_RETRY_TIMES=3`、`TASK_EXECUTION_TIMEOUT=30`。
- **E-04**：`scheduleRetry` 的重试延迟为 `RETRY_DELAY * attempt`（第 333 行，`RETRY_DELAY = 1000`），即 1s/2s 线性递增，无指数退避、无抖动；单次尝试的 `orTimeout` 为 30s（第 296 行），尝试次数上限 3（第 56 行）。
- **E-05**：`getConsumerCountForQueue`（第 244–248 行）以 `listenerConfigs.size()` 计算每队列消费者数，且调用发生在 `putIfAbsent`（第 132 行）之后，消费并发度取决于 Bean 注册顺序。
- **E-06**：`startListenerTask` 在发现同队列已注册时直接 `return`（第 111–115 行、132–136 行），未销毁本方法内已通过 `client.getDelayedQueue(blockingQueue)` 创建的对象。
- **E-07**：`GXRedissonMQUtils` 的 `TOPIC_CACHE` / `LISTENER_REGISTRATION_CACHE` 为 `static`（第 32–33 行），绑定创建时的 `RedissonClient`；`GXRedissonMQPostProcessor.destroy`（第 108–127 行）仅在本地缓存已空时才整体清空。
- **E-08**：`GXRedissonStreamImmediateMQ` 在 `handler == null` 时直接 `ack`（第 195–200 行）；DLQ 写入失败时 `return` 且不 `ack`（第 184–190 行）。
- **E-09**：`GXRedissonStreamDelayedMQ.transferDueMessages` 以全局固定锁 `DELAY_LOCK_KEY` 包住所有 topic 的转移（第 149–166 行），单条消息经历 `hash.get → transferSet.add → zset.remove → publish → hash.remove → transferSet.remove`（第 187–210 行），单轮上限 200 条。
- **E-10**：`GXRedissonUtils.safeUnlock` 先 `isLocked()` 再 `isHeldByCurrentThread()` 再 `unlock()`（第 362–370 行）；`executeWithLock` 获取超时时返回 `null`（第 180–184 行）；`getCounterValue` 异常时返回 `0`（第 111–119 行）。
- **E-11**：`GXRedissonSpringDataConfig.splitAddresses`（第 147–152 行）对只含分隔符的地址返回空数组，随后 `addresses[0]`（第 111–113 行）会抛数组越界而非配置可读错误；`isClusterConfig` 以 key 名是否包含 "cluster" 判定（第 154–156 行）。
- **E-12**：`GXRedissonStreamMQManager.start()` 依次启动三个组件后置 `started = true`（第 53–58 行），中途异常会导致已启动线程无法被 `stop()` 回收。
- **E-13**：依赖侧事实（本地 `redisson-4.7.0-sources.jar`）：`Redisson.getDelayedQueue` 在首次构造时打印 `RDelayedQueue object is deprecated ... Use RReliableQueue object instead`；`QueueTransferService.schedule/remove` 按队列名做**引用计数**，重复创建只 `incUsage`，`destroy()` 仅 `decUsage` 一次。

发现清单（分级）：

- **F-01（高）订阅缓存无法自愈**：`unsubscribe` 抛异常或监听器被外部移除后，缓存条目仍在，后续 `subscribe` 直接返回旧 `listenerId` 并将其当作成功——调用方认为已订阅，实际无消费者，消息静默丢失（E-01）。
- **F-02（高）可靠投递退化为至多一次**：消息移出 Redis 后只存在于进程内存，进程崩溃或 `destroy` 未走到重投分支即永久丢失；"延迟队列可靠转发"的对外承诺与实现不一致（E-02）。
- **F-03（高）无处理器即丢弃 + 毒消息常驻**：stream 消费者在无 handler 时 `ack` 丢弃；DLQ 写入失败时不 `ack`，畸形消息永久 pending 并每轮重投，且重投不递增重试计数，永远无法升级为死信（E-08）。
- **F-04（高）延迟转移全局锁 + 串行往返**：跨应用共用的固定锁键把全部 topic 串行化，单条消息 6 次往返，单实例慢或 handler 慢时抢占失败的实例持续空转，吞吐与最慢节点耦合（E-09）。
- **F-05（中）转发链路无背压**：`localQueue` 有界（5000），但 in-flight 只受"超时 × 消费速率"间接约束，无信号量或窗口上限；handler 变慢时内存与待办 future 线性增长（E-03）。
- **F-06（中）重试节奏固定且窗口不可控**：重试间隔为 1s/2s 线性递增（无指数退避、无抖动），单次尝试可占用 30s 超时，最坏情况下一条消息在 in-flight 中滞留 93 秒（3 × 30s 超时 + 1s + 2s 退避）；故障恢复后仍按固定节奏倾泻（E-04）。
- **F-07（中）消费者并发度不确定**：同一份配置在不同启动顺序下每队列消费者数不同，容量规划与压测结果不可复现（E-05）。
- **F-08（中）重复注册路径资源泄漏**：队列已注册时提前返回，已创建的延迟队列对象未 `destroy()`；因上游按队列名做引用计数，抬高后的计数不会回落，转移任务在容器关闭后仍不会停止（E-06、E-13）。
- **F-09（中）静态缓存跨容器泄漏**：静态缓存持有旧 `RedissonClient` 派生的 topic 句柄，上下文重建/客户端重启后可能继续操作失效客户端；`destroy` 的清理条件过窄（E-07）。
- **F-10（中）业务异常被吞**：`wrapListener` 捕获并记录业务监听器异常后不再抛出（第 294–302 行），Redisson 视为消费成功，可靠主题退化为尽力投递，且无补偿入口。
- **F-11（中）锁与计数器语义/开销**：加解锁多 2 次网络往返；加锁超时返回 `null` 与"操作正常返回 `null`"不可区分；计数器读异常返回 `0` 掩盖故障（E-10）。
- **F-12（中）stream 去重与恢复不完整**：去重为 check-then-act，`markProcessed` 失败仍 `ack`；pending 恢复只取头部 N 条且无 idle 过滤，头部受阻时后续消息长期饥饿（第 202–229 行、265–270 行）。
- **F-13（中）连接配置边界**：非法地址（如仅分隔符）抛数组越界而非可诊断错误；集群判定依赖配置键命名，非集群多地址/哨兵形态无明确路径（E-11）。
- **F-14（中）生命周期不闭合**：stream 组件启动中途失败留下不可回收线程；`blockingTimeoutMillis = 0` 被接受并导致阻塞读永不返回，停止流程只能超时返回（E-12）。
- **F-16（中）建立在弃用 API 之上**：延迟转发链路依赖 `RDelayedQueue`，上游 4.7.0 已标注弃用并在构造时输出 error 级提示，推荐替代为 `RReliableQueue`；该链路一旦在上游被移除即整体失效，属"升级即断"的契约风险（E-13）。
- **F-15（低）缓存语义待书面化**：`updateCacheExpiredTime` 对"无过期时间"（TTL = -1）直接返回 `true` 但不设置过期；`getBucketAllData` 全量物化键与值。二者已被既有测试锁定，需在报告中明确为"既定契约"而非缺陷。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 审查结论可复核、可定位 (Priority: P1)

框架维护者在决定"是否可以在生产启用该模块的 MQ 与缓存能力"时，需要拿到分级结论，而不是笼统的"看起来没问题"。每条结论都要能直接跳到代码位置，并有一键可复现的验证方式。

**Why this priority**: 审查类工作的唯一价值是"结论可信"。结论不能复核，后续计划与修复都建立在猜测之上。

**Independent Test**: 随机抽取结论条目，按报告给出的位置与命令复现，断言"看到的现象与结论描述一致"；对高风险项必须能构造出故障现场。

**Acceptance Scenarios**:

1. **Given** 一条"订阅缓存无法自愈"的结论，**When** 使 `unsubscribe` 失败后再调用 `subscribe`，**Then** 可观察到返回成功但监听器未注册，与结论一致。
2. **Given** 一条"消息移出 Redis 后仅存于内存"的结论，**When** 在转发完成前终止进程，**Then** 消息在 Redis 与下游均不可见，与结论一致。
3. **Given** 一条"延迟转移持全局锁"的结论，**When** 单实例 handler 人为变慢，**Then** 其他实例当轮转移全部跳过，与结论一致。

---

### User Story 2 - 并发与资源释放风险可被验证 (Priority: P1)

运维与开发需要知道：线程池与虚拟线程在何种情况下会不释放、并发度是否稳定、容器关闭时消息与资源是否收敛。这些问题在单线程功能测试中不会暴露，必须用并发场景固定。

**Why this priority**: 线程泄漏与并发度漂移属于"上线后才发现"的故障，且会直接表现为消息积压或重复消费。

**Independent Test**: 在隔离测试中构造"重复注册同队列""启动中途失败""上下文重复重建""容器关闭时有在途消息"四类场景，断言线程数、队列长度、注册数量与资源销毁次数的收敛结果。

**Acceptance Scenarios**:

1. **Given** 两个 Bean 声明同一个延迟队列，**When** 容器启动完成，**Then** 只存在一组消费者与抓取任务，且被跳过的那次注册不残留延迟队列对象。
2. **Given** 延迟队列消费者正在处理消息，**When** 容器关闭，**Then** 在途消息与本地队列消息全部回到 Redis，且进程退出后 Redis 中无遗留消息。
3. **Given** 同一份配置以不同 Bean 注册顺序启动两次，**When** 比较每队列消费者数，**Then** 两次结果一致（或差异被报告中明确认定为"待修复缺陷"）。
4. **Given** 应用上下文被关闭后重新创建，**When** 再次订阅同一主题，**Then** 使用的是新客户端的订阅句柄，不出现"订阅成功但消息不来"。

### User Story 3 - 性能瓶颈定量化 (Priority: P2)

维护者需要判断该模块能否支撑目标吞吐。结论不能是"可能有性能问题"，而要给出可复算的口径：单条消息多少次网络往返、临界区持锁多久、队列与内存上限是多少、瓶颈随规模如何变化。

**Why this priority**: 性能结论若无口径，计划阶段无法给出"改到什么程度算达标"。

**Independent Test**: 按报告中的统计口径（往返次数 × 单轮上限 × 锁持有窗口）复算一遍，断言与报告数值一致；对可执行项跑一次批量输入冒烟，记录吞吐与积压。

**Acceptance Scenarios**:

1. **Given** 延迟 stream 转移路径，**When** 按报告统计单条消息的 Redis 往返次数，**Then** 数值与代码路径逐条对应且可复算。
2. **Given** 本地队列容量 5000，**When** 持续注入超过处理能力的消息，**Then** 报告给出"内存增长与拒绝策略"的可观测上限，而不是"理论上不会满"。
3. **Given** 锁工具的单次加解锁，**When** 统计网络往返次数，**Then** 报告给出次数与可优化点，且不改变现有锁语义。
4. **Given** 可靠主题批量发布，**When** 注入 1000 条消息，**Then** 报告给出成功数、失败数与耗时口径，并说明失败是否被静默吞掉。

### User Story 4 - 对外契约与文档一致 (Priority: P3)

使用方依赖 `AGENTS.md`、模块手册与公开方法签名判断行为。文档描述与实现不一致时，必须作为独立发现记录，而不是在审查中顺手改掉。

**Why this priority**: 契约漂移的排查成本高，但不直接影响运行时正确性，故低于前三项。

**Independent Test**: 逐条核对文档声明的"可靠主题只订阅一次""延迟队列失败会重试与回退""缓存 TTL 语义"与实现，断言每条声明有明确判定（一致 / 不一致 / 未覆盖）。

**Acceptance Scenarios**:

1. **Given** `AGENTS.md` 声明"延迟队列转发失败后的重试、回退和清理策略必须保持可观测"，**When** 核对实现，**Then** 报告给出"可观测"的具体证据或缺失点。
2. **Given** 文档声明订阅幂等，**When** 订阅在失败后重试，**Then** 报告指出幂等是否成立及其失效条件。
3. **Given** 公开方法的异常语义（加锁超时、计数器异常），**When** 核对签名与实现，**Then** 报告逐条给出"返回值如何表达失败"。

---

### User Story 5 - 结论可驱动后续修复排期 (Priority: P3)

计划阶段需要把发现直接转成任务：每条发现都应有独立编号、严重级别、影响面、修复方向与"能在旧代码失败、在新代码通过"的回归测试设计。

**Why this priority**: 审查不是终点；不能落到可执行任务的结论，等于没有结论。

**Independent Test**: 抽取任一发现，检查是否同时具备"编号 + 级别 + 位置 + 触发条件 + 影响 + 证据 + 复现方式 + 回归测试思路"八项，缺任一项即视为不合格。

**Acceptance Scenarios**:

1. **Given** 一条高危发现，**When** 交由计划阶段，**Then** 无需补充上下文即可拆出"测试先行"的任务。
2. **Given** 一条被判定为"既定契约"的行为（如无过期时间条目不被刷新），**When** 查阅报告，**Then** 明确标注为契约而非缺陷，避免被误改。

### Edge Cases

- Redis 不可用或正在关闭时，抓取线程、消费者、重试调度器的停止顺序与最终状态。
- 应用上下文关闭后再次创建（测试环境常见），静态缓存中的旧客户端句柄与旧监听器。
- 同一秒内多个 Bean 声明同一延迟队列，重复注册的判定与资源清理。
- 本地队列被填满（5000）时的消息回退路径，以及回退再次失败时的最终归属。
- 消息在"移出 Redis"与"写入 in-flight"之间的进程崩溃窗口。
- 转发过程超时（30 秒）与重试次数用尽（3 次）叠加时的总等待时间与消息最终位置。
- Stream 消费者组已存在（BUSYGROUP）、消费者组创建失败、无 handler、消息体畸形、DLQ 写入失败。
- 阻塞读超时被配置为 0 或极大值时的停止行为。
- 连接地址只含分隔符、地址含空格、键名含 "cluster" 但实为单节点。
- 分布式锁获取超时、释放失败、持有线程判定失败时的返回值语义。
- 缓存条目无过期时间（TTL = -1）时刷新过期时间的预期行为。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 审查 MUST 覆盖 `leaf-base-redisson` 全部 51 个生产源码文件、`application.yml` 与既有 38 个用例；每个文件 MUST 有明确判定（无缺陷 / 风险 / 缺陷 / 未覆盖原因），不得跳过。
- **FR-002**: 每条结论 MUST 标注所属维度（逻辑正确性 / 线程安全 / 性能）、严重级别（高 / 中 / 低）、代码位置（文件 + 行区间）、触发条件与影响面。
- **FR-003**: 每条结论 MUST 附带可复现方式：既有测试、可新增的回归用例设计、或明确的构造步骤；仅凭阅读得出的判断 MUST 标注为"未验证假设"，不得混入已确认结论。
