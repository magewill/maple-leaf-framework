## 背景 / 现象

F-16：`GXBeanCopierCache` 用 `WeakKeyConcurrentMap<String, BeanCopier>` 存储，`genKey` 每次调用都 `new` 一个 `String` 键，调用方不保留强引用。

需要澄清命中率：Hutool 的 `WeakObj.equals` 是**按 referent 比较**（`ObjUtil.equals` → `Objects.equals`），hashCode 在构造时取 referent 的 hashCode，所以只要键对象还没被回收，`get(newKey)` 是**能命中**的。真正的缺陷是**条目寿命不可控**——`ReferenceConcurrentMap` 每次操作都先 `purgeStale()` 清一次引用队列，键一旦不可达，下一次 GC 就会把条目清掉。于是缓存退化成"GC 之间有效、GC 之后全丢"，命中率完全取决于 GC 频率；应用里 young GC 通常每隔几秒一次，等于反复执行 `BeanCopier.create`（生成字节码），持续推高 metaspace。

`GXCglibUtils.copyList` 中的 per-call 局部缓存（`localBeanCopierCache` + `lastSourceClass/lastTargetClass/lastBeanCopier`）即为绕开该问题的补丁，但 `copy(...)` 单次调用完全无法受益。

## 变更前

- `cache` 为 `WeakKeyConcurrentMap<String, BeanCopier>`；`genKey(Class, Class, boolean)` 每次新建 `String` 作为弱引用键。
- `GXCglibUtils.copyList` 用三个 `lastXxx` 变量 + 惰性初始化的局部 Map 维护"上一个 copier"，逻辑分支复杂且易改错。
- `GXPerformanceBudgetAuditTest` 以反射断言 `genKey` 每次返回新实例、`cache` 字段类型名包含 `WeakKey`，锁定的是缺陷行为。

## 变更后

- `cache` 改为 `ClassValue<ConcurrentMap<CopierKey, BeanCopier>>`：以源类型作为 `ClassValue` 槽位，槽内以 `record CopierKey(targetClass, useConverter)` 为强引用键。同一类型对只生成一次字节码；条目挂在 `Class` 上，Class 卸载时随之释放，不引入 ClassLoader 泄漏，也不再需要弱引用键。
- 新增 `size(Class<?> srcClass)`，用于测试与诊断（返回指定源类型下已缓存的 copier 数量）。
- `GXCglibUtils.copyList` 简化为单个 `HashMap<CopierCacheKey, BeanCopier>` + `computeIfAbsent`，删除 `lastSourceClass` / `lastTargetClass` / `lastBeanCopier` 三个状态变量与惰性初始化分支。
- `GXPerformanceBudgetAuditTest` 的两条特征化断言翻转为修复后语义：同一类型对 `assertSame`、converter/非 converter 实例分离、100 次重复查找缓存条目不增长；类注释同步更新（XSS 包装器构造期读全量请求体仍为当前行为）。
