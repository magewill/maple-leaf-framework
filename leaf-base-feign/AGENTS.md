# AGENTS.md - leaf-base-feign

本文档用于指导 `leaf-base-feign` 模块的后续迭代开发。修改本模块时，优先保证 Feign 调用链路的鉴权一致性、请求头透传稳定性、错误解码可预期性，以及 Spring Boot 集成行为可验证，避免无关重构。

## 通用硬性规则

1. 每次修改只能触碰当前 Maven 模块；确需跨模块时，先说明触发原因、受影响模块、替代方案和最小改动集合。
2. 现有代码已经在生产环境使用，不得随意更改对外接口规范、配置语义、默认行为、异常语义或序列化契约；必须变更时，同步补充兼容说明、迁移路径和回归测试。
3. 在确保原有功能正确的前提下完善实现；修改既有逻辑前，先用测试锁定当前成功、失败、空值、边界和回归路径。
4. 基础框架代码必须优先审查性能、线程安全、资源释放和并发可见性；线程池与虚拟线程都能满足需求时，优先使用虚拟线程。
5. 空值处理必须支持 JSpecify 规范：新增或修改 API、DTO、配置属性、回调、集合元素和异步结果时，明确 `@NullMarked`、`@Nullable` 或等价约束，让空值语义可被 IDE、编译检查和测试验证。
6. 严格遵循测试驱动最佳实践：先写或调整能暴露问题的测试，再实现最小代码变更，最后运行模块级验证命令。
7. 涉及改动的点都要检查测试用例是否完整；覆盖不足时补齐成功、失败、异常、空值、边界和回归场景。
8. 功能只有在 Spring Boot 应用运行后才能验证时，使用 `@SpringBootTest` 或等价方式模拟真实启动后的 Bean 装配、条件配置、AOP、监听器、异步流程和配置绑定。
9. 修改线程安全或性能相关代码时，必须补充严格测试；覆盖并发访问、重复执行、超时、取消、资源释放和关键指标，无法自动化时在提交说明写清手工压测命令、样本规模和观察指标。
10. 所有 `log` 日志内容必须使用 ASCII 字符，避免不同运行环境、终端编码或日志采集链路出现乱码。
11. 不要随便把已存在代码抽取成单独方法或类；只有抽取后的逻辑至少被两个位置复用，或能显著降低复杂度且不破坏语义时，才允许抽取。
12. 删除方法、类、变量上的冗余注释；清理 Javadoc 中重复、空泛或仅复述签名的信息，只保留语义说明、边界条件、异常约定等必要内容。
13. 复杂方法、复杂类、公共扩展点或使用方式不直观的能力，应补充必要 Javadoc；使用门槛较高时，给出简短使用示例。
14. 精准命令胜过陈词滥调：直接给出 `mvn -pl 当前模块 test`、`rg "类名|方法名" 当前模块/src/test` 这类具体步骤，避免“确保代码质量”“提升项目可维护性”等抽象套话。
15. 控制 `AGENTS.md` 长度与结构，建议保持在 200 行以内；规范继续增多时，在子目录创建领域指南，本文件只保留入口链接和必须遵守的红线。
16. 持续优化迭代：`AGENTS.md` 是动态文档；当 Agent 的实际输出与预期目标出现偏差时，把偏差改写成下一次可执行、可检查的规则。

## 1. 模块定位

`leaf-base-feign` 是 Maple Leaf Framework 的 Feign 基础支持模块，当前主要提供以下能力：

1. `GXFeignService`：定义 Feign 场景下的默认契约与可覆盖扩展点，包括认证 token 生成与校验、traceId 获取、平台标识透传、HMAC 相关能力以及敏感请求头约定。
2. `GXFeignConfig`：提供 Feign 全局配置，统一注册日志级别、请求拦截器、错误解码器等基础 Bean。
3. `GXFeignRequestInterceptor`：负责在 Feign 请求发起前透传认证 token、平台标识、traceId、注解声明的请求头，以及补充通用请求头。
4. `GXFeignCustomErrorDecoder`：对常见 HTTP 错误码进行统一解码，转换为框架层可消费的业务异常。
5. `GXFeignAuthTokenAspect`：在标注 `@GXHttpInvokerAuthToken` 的方法或类型上执行 Feign 调用 token 校验，保证内部调用鉴权规则一致。
6. `GXFeignHeader`：声明式定义需要从当前请求透传到 Feign 调用中的请求头。

本模块不承载具体业务系统的远程调用编排、业务 DTO、业务异常翻译规则或某个单一服务专属的 Feign 客户端实现。

## 2. 目录职责

1. `annotation`：Feign 相关注解定义，只放声明式契约，不放运行时流程代码。
2. `aspect`：Feign 鉴权校验相关切面逻辑，重点保证注解解析顺序、AOP 代理兼容性和异常语义稳定。
3. `codec`：Feign 错误解码器，负责远程错误到框架异常的映射与日志输出。
4. `config`：Feign 自动装配与基础 Bean 配置，避免混入业务判断。
5. `interceptor`：Feign 请求发起前的上下文透传、公共请求头补充与请求增强逻辑。
6. `service`：Feign 模块对外暴露的可扩展 SPI 契约及默认实现方法。

## 3. 强制开发规则

1. 所有 `log` 日志中的内容都必须使用 ASCII 字符，禁止新增或保留非 ASCII 日志文案，避免不同终端、采集链路或编码配置下出现乱码。
2. 涉及到改动的点，都要同步查看测试用例是否覆盖完整；如果当前测试缺失、失效或覆盖不足，必须补齐后再提交。
3. 不要随便将已存在的代码抽取成单独的方法或者类；只有当抽取后的逻辑可以被两个以上的位置复用，或能够明显降低复杂度与维护成本时，才允许抽取。
4. 将方法、类、变量上的冗余注释去掉；能通过命名、类型和局部代码结构直接表达清楚的内容，不再保留重复解释。
5. 清理 Javadoc 中的冗余信息，只保留必要的文档内容；在复杂的方法、类、扩展点上适当补充 Javadoc，必要时提供简短使用示例，说明典型用法、边界条件和扩展方式，方便后续使用者参考。
6. 修改 `GXFeignService` 默认方法时，必须评估其是否影响已有实现类的覆盖行为、环境配置键、异常语义和上下游兼容性。
7. 修改 `GXFeignRequestInterceptor` 时，必须优先保证请求头透传行为幂等，避免重复 header、覆盖顺序错误或在无 Web 上下文时抛出异常。
8. 修改 `GXFeignAuthTokenAspect` 时，必须保持方法级注解优先于类级注解的解析语义，同时考虑代理对象、AOP 最具体方法解析和无 Bean 场景下的错误处理。
9. 修改 `GXFeignCustomErrorDecoder` 时，必须明确哪些 HTTP 状态码走自定义异常映射，哪些继续走 Feign 默认解码，避免静默改变线上异常分类。
10. 配置类中的 Bean 应保持单一职责和可覆盖性；新增全局 Feign 行为前，先确认是否适合做成默认 Bean，而不是强耦合到全部客户端。
11. 每次修改都只能修改当前 Maven 模块 `leaf-base-feign` 内的文件；不得修改其它 Maven 模块、根模块公共配置或跨模块共享文件，除非用户明确要求。
12. 现有代码已经在生产环境使用，不得随意更改对外接口规范；涉及公开类、方法签名、注解语义、配置键、默认 header、异常类型或异常语义的调整，必须优先保持向后兼容。
13. 本模块作为基础框架，代码的性能、线程安全性非常重要；新增共享状态、缓存、异步逻辑、拦截器状态或 Bean 生命周期逻辑时，必须评估并验证并发访问下的正确性。
14. 在线程池与虚拟线程都能满足场景需求时，优先使用虚拟线程；只有在需要固定资源隔离、调度策略或与既有执行器契约兼容时，才保留传统线程池。
15. 在确保原有功能正确性的条件下进行完善；修改已经存在的逻辑时，不得改变现有逻辑的正确性、兼容性和线上可预期行为。
16. 严格遵循测试驱动最佳实践；修复缺陷或新增能力时，优先补充能暴露问题或描述目标行为的测试，再实现代码并通过回归验证。

## 4. 测试要求

1. 测试用例要覆盖全面，至少覆盖成功路径、失败路径、异常路径、空值路径和边界条件。
2. 如果该功能需要在 Spring Boot 应用运行的情况下才能测试，那么测试用例就应该模拟真实 Spring Boot 应用启动之后再测试，优先使用接近真实容器行为的 `@SpringBootTest`、切面代理、Bean 装配和请求上下文验证，而不是只做纯单元测试。
3. 严格遵循测试驱动最佳实践：先用测试描述预期行为或复现缺陷，再进行实现和重构；已有行为调整必须保留或补充回归测试，避免只依赖人工推断。
4. `GXFeignRequestInterceptor` 相关改动至少要覆盖：
   - 有 `GXFeignService` Bean 与无 Bean 两种场景。
   - token、platform、traceId 的透传和回退生成逻辑。
   - `@GXFeignHeader` 声明的请求头透传。
   - 无 `HttpServletRequest` 上下文时的安全行为。
5. `GXFeignAuthTokenAspect` 相关改动至少要覆盖：
   - 方法级注解、类级注解、生效值不匹配时的跳过逻辑。
   - `GXFeignService` 缺失时的异常。
   - token 校验成功与失败分支。
   - 代理类和最具体方法解析行为。
6. `GXFeignCustomErrorDecoder` 相关改动至少要覆盖：
   - 自定义处理状态码的异常映射。
   - 非自定义状态码回退到默认解码。
   - 响应体为空、可读取、读取失败三类分支。
7. `GXFeignService` 默认实现相关改动至少要覆盖：
   - 配置缺失时的异常行为。
   - token 生成与校验逻辑。
   - traceId 回退顺序。
   - HMAC 与敏感头默认值是否保持兼容。
8. 涉及共享状态、缓存、异步执行、线程池或虚拟线程的改动，必须补充并发、安全发布、资源释放或线程隔离相关测试。
9. 提交前至少保证模块级测试命令可运行：`mvn -pl leaf-base-feign test`。

2. 是否检查过相关测试是否完整，并补齐了缺失场景。
3. 是否引入了非 ASCII 的日志内容。
4. 是否做了没有复用价值的方法或类抽取。
5. 是否删除了冗余注释，并为复杂逻辑补充了必要 Javadoc 或示例。
6. 是否改变了公共 header 名称、配置键、异常消息、状态码映射或切面触发条件。
7. 是否验证了无 Web 请求上下文、无 Bean、空 token、空 traceId 等防御性分支。
8. 是否只修改了 `leaf-base-feign` 当前 Maven 模块内的文件，且没有越界改动其它模块或根模块配置。
9. 是否确认对外接口规范保持兼容，包括公开 API、注解语义、配置键、异常类型和默认行为。
10. 是否评估了性能、线程安全性、共享状态和并发访问风险；线程池与虚拟线程都可行时，是否优先选择虚拟线程。
11. 是否遵循测试驱动最佳实践，先补充目标行为或缺陷复现测试，再实现和回归验证。
