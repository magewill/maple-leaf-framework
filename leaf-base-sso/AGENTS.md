# AGENTS.md - leaf-base-sso

本文档用于指导 `leaf-base-sso` 模块后续迭代开发。修改本模块时，优先保持现有 SSO 行为兼容、接口语义稳定和安全策略一致，避免无关重构。

## 通用硬性规则

1. 每次修改只能触碰当前 Maven 模块；确需跨模块时，先说明触发原因、受影响模块、替代方案和最小改动集合。
2. 现有代码已经在生产环境使用，不得随意更改对外接口规范、配置语义、默认行为、异常语义或序列化契约；必须变更时，同步补充兼容说明、迁移路径和回归测试。
3. 在确保原有功能正确的前提下完善实现；修改既有逻辑前，先用测试锁定当前成功、失败、空值、边界和回归路径。
4. 基础框架代码必须优先审查性能、线程安全、资源释放和并发可见性；线程池与虚拟线程都能满足需求时，优先使用虚拟线程。
5. 空值处理必须支持 JSpecify 规范：新增或修改 API、DTO、配置属性、回调、集合元素和异步结果时，明确 `@NullMarked`、`@Nullable` 或等价约束，让空值语义可被 IDE、编译检查和测试验证。
6. 严格遵循测试驱动最佳实践：先写或调整能暴露问题的测试，再实现最小代码变更，最后运行模块级验证命令。
7. 涉及改动的点都要检查测试用例是否完整；覆盖不足时补齐成功、失败、异常、空值、边界和回归场景。
8. 功能只有在 Spring Boot 应用运行后才能验证时，使用 `@SpringBootTest` 或等价方式模拟真实启动后的 Bean 装配、条件配置、AOP、监听器、异步流程和配置绑定。
9. 修改线程安全或性能相关代码时，必须补充严格测试；覆盖并发访问、重复执行、超时、取消、资源释放和关键指标，无法自动化时在提交说明写清手工压测命令、样本规模和观察指标。
10. 所有 `log` 日志内容必须使用 ASCII 字符，避免不同运行环境、终端编码或日志采集链路出现乱码。
11. 不要随便把已存在代码抽取成单独方法或类；只有抽取后的逻辑至少被两个位置复用，或能显著降低复杂度且不破坏语义时，才允许抽取。
12. 删除方法、类、变量上的冗余注释；清理 Javadoc 中重复、空泛或仅复述签名的信息，只保留语义说明、边界条件、异常约定等必要内容。
13. 复杂方法、复杂类、公共扩展点或使用方式不直观的能力，应补充必要 Javadoc；使用门槛较高时，给出简短使用示例。
14. 精准命令胜过陈词滥调：直接给出 `mvn -pl 当前模块 test`、`rg "类名|方法名" 当前模块/src/test` 这类具体步骤，避免“确保代码质量”“提升项目可维护性”等抽象套话。
15. 控制 `AGENTS.md` 长度与结构，建议保持在 200 行以内；规范继续增多时，在子目录创建领域指南，本文件只保留入口链接和必须遵守的红线。
16. 持续优化迭代：`AGENTS.md` 是动态文档；当 Agent 的实际输出与预期目标出现偏差时，把偏差改写成下一次可执行、可检查的规则。

## 1. 模块定位

`leaf-base-sso` 是 Maple Leaf Framework 的单点登录与鉴权基础模块，负责：

1. SSO Token 的生成、解析、缓存同步与校验。
2. 登录态管理（Cookie 写入、清理、SameSite/安全属性、重定向登录/登出）。
3. 登录拦截与权限拦截（URL 白名单、注解跳过、权限注解校验）。
4. SSO 扩展点（`GXSSOPlugin`、`GXSSOAuthorization`、拦截器扩展服务）。
5. 验证码能力（静态图/GIF、会话存储与校验）。
6. 本地配置与 Nacos 配置读取（SSO 配置、白名单配置）。

不在本模块内承载具体业务域规则或业务流程编排。

## 2. 目录职责

1. `annotation`：SSO 相关注解定义（登录用户、权限注解）。
2. `service` / `service.impl`：SSO 核心服务抽象与默认实现。
3. `web.interceptor`：登录拦截与权限拦截实现。
4. `web.handler`：未登录/无权限场景处理策略。
5. `properties`：SSO 与白名单配置模型（含 local/nacos 子目录）。
6. `oauth`：权限校验接口抽象。
7. `plugins`：SSO 生命周期插件扩展点。
8. `captcha`：验证码生成、存储和校验能力。
9. `utils` / `constant` / `enums` / `dto`：工具类、常量、枚举和传输对象。

## 3. 强制开发规则

1. 所有 `log` 日志内容必须使用 ASCII 字符，禁止新增或保留非 ASCII 日志文案。
2. 涉及改动的点，必须同步检查对应测试用例是否完整覆盖；覆盖不足时必须补充测试。
3. 不要随意把已存在代码抽取成单独方法或类；仅当抽取后的逻辑能被两个及以上位置复用，或显著降低复杂度时才允许抽取。
4. 删除方法、类、变量上的冗余注释，避免注释重复描述代码字面含义。
5. 清理 Javadoc 中的冗余信息，只保留必要的文档内容；在复杂的方法、类、扩展点上适当补充 Javadoc，必要时提供简短使用示例，说明典型用法、边界条件和扩展方式，方便后续使用者参考。
6. 每次修改都只能修改当前 Maven 模块，不得修改其它模块。
7. 现有代码已经在生产环境使用，不得随意更改对外接口规范、配置契约、扩展点契约或默认行为。
8. 在确保原有功能正确性的条件下进行完善；修改已有逻辑时，不得改变现有逻辑的正确性。
9. 作为基础框架模块，代码必须重点关注性能、线程安全性和资源释放，避免引入共享可变状态、阻塞热点或不必要的对象分配。
10. 在线程池与虚拟线程都能满足场景要求时，优先使用虚拟线程；如继续使用线程池，必须有明确的兼容性、性能或资源控制理由。
11. 扩展点默认实现必须是安全默认值：不能静默放行、静默返回空业务数据或绕过服务端状态校验。
12. 安全相关默认行为（Token 校验、Cookie 安全属性、登录拦截、权限校验）变更前，必须先评估兼容性和风险。
13. 新增配置项必须有明确默认值、失效语义和兼容策略，避免隐式行为变化。

## 4. 测试要求

1. 任何功能改动必须先看现有测试是否覆盖：成功路径、失败路径、异常路径、边界条件。
2. 测试用例要覆盖全面；如果功能依赖 Spring 容器、自动配置、拦截器链、Web 请求上下文或 Bean 装配，测试必须使用接近真实运行形态的 Spring Boot 启动测试（如 `@SpringBootTest`）。
3. 重点覆盖以下能力：
   - Token 获取与校验（Header/Cookie/缓存命中与失效）。
   - 登录态写入与清理（Cookie 属性、缓存同步、降级逻辑）。
   - 登录拦截与白名单策略（注解跳过、AJAX/普通请求分支）。
   - 权限拦截策略（URL 权限模式、注解权限模式、无权限处理）。
   - 验证码生成/存储/校验。
4. 至少保证模块级测试命令可执行：`mvn -pl leaf-base-sso test`。

## 5. 变更前检查清单

1. 是否影响 `GXSSOService`、`GXAbstractSSOService`、`GXSSOSupportService` 的对外语义。
2. 是否影响登录拦截链和权限拦截链的顺序与行为。
3. 是否影响 Token 与缓存一致性校验、踢出登录、登出清理逻辑。
4. 是否新增或修改了非 ASCII 的日志文本。
5. 是否引入了不必要的方法/类抽取。
6. 是否移除了冗余注释并补齐了必要 Javadoc/示例。
7. 是否已补充或更新测试，且覆盖本次改动风险点。
8. 是否仅修改了 `leaf-base-sso` 当前 Maven 模块。
9. 是否保持了已有对外接口规范、配置契约、扩展点契约和默认行为兼容。
10. 是否评估了性能、线程安全性、资源释放和虚拟线程优先使用的适用性。
11. 是否避免了扩展点默认实现静默放行或静默返回空业务数据。

## 6. 提交说明建议

1. 涉及登录态、拦截器、权限、Token 的变更，PR 描述必须说明行为变化和兼容性影响。
2. 涉及安全行为调整时，PR 描述需包含风险评估和回滚方案。
3. 提交前确认新增/修改日志均为 ASCII。
4. 提交前确认测试已覆盖改动点，并在 PR 中说明关键验证结果。
