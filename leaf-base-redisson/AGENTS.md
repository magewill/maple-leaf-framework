# AGENTS.md - leaf-base-redisson

本文档用于指导 `leaf-base-redisson` 模块的后续开发、审查和测试。所有变更都必须优先保护现有生产功能、对外契约、Redisson 连接配置、缓存行为、可靠主题和延迟队列转发链路的正确性。

## 1. 模块边界

`leaf-base-redisson` 是 Maple Leaf Framework 的 Redisson 基础能力模块，负责：

1. Redisson Client 与 Spring Cache 的统一装配。
2. 单机、集群连接配置解析和线程参数配置。
3. Redisson 可靠主题的发送、订阅、取消订阅和本地监听缓存管理。
4. Redisson 延迟队列的发送、清理和消息转发到可靠主题。
5. MQ 监听器在 Spring Bean 生命周期中的注册、注销和资源释放。
6. 分布式锁、计数器、限流、KV、Map Cache 等基础工具能力。
7. 本地配置与 Nacos 配置读取。

本模块不承载业务流程编排、业务域规则和其它 Maven 模块的职责。

## 2. 目录职责

1. `config`：Redisson、Spring Cache、Redisson MQ 的核心装配。
2. `properties`：配置模型定义，包含 `local` 和 `nacos` 子目录。
3. `util`：缓存、锁、限流、主题、延迟队列等通用 Redisson 工具。
4. `services` / `services.impl`：面向业务模块的缓存服务抽象与实现。
5. `listener`：MQ 监听契约和延迟消息处理契约。
6. `processor`：监听器自动注册、转发执行、生命周期清理。
7. `annotation`：延迟队列转发注解定义。
8. `adapter`：对外兼容适配。

## 3. 强制开发规则

1. 每次修改只能修改当前 Maven 模块 `leaf-base-redisson` 内的文件，不得顺手修改其它模块。
2. 现有代码已经在生产环境使用，不得随意更改对外接口规范、配置语义、注解参数、异常语义和已有业务语义。
3. 在确保原有功能正确性的前提下进行完善；修改已有逻辑时，不得改变现有逻辑的正确性。
4. 所有 `log` 日志内容必须使用 ASCII 字符，禁止新增或保留非 ASCII 日志文案。
5. 涉及改动的点，必须查看现有测试用例是否完整覆盖；覆盖不足时必须补充测试。
6. 严格遵循测试驱动最佳实践：先明确可验证行为和回归风险，再补充或调整测试，最后修改实现。
7. 不要随意把已存在代码抽取成单独方法或类；仅当抽取后的逻辑能被两个及以上地方复用，或确实能降低复杂度并保持语义清晰时才允许抽取。
8. 删除方法、类、变量上的冗余注释，避免注释重复描述代码字面含义。
9. 清理 Javadoc 的冗余信息，只保留必要文档；复杂方法、复杂类、对外扩展点可以适当补充 Javadoc 和简短使用实例。
10. 作为基础框架模块，代码变更必须重点关注性能、资源释放、并发可见性和线程安全性。
11. 在线程池与虚拟线程都能满足需求的场景中，优先使用虚拟线程；若继续使用线程池，必须说明容量、生命周期、背压和拒绝策略的合理性。
12. 变更连接配置解析逻辑前，必须评估单机/集群判断、地址解码、线程参数默认值和鉴权字段的兼容性影响。
13. 变更 MQ 监听注册、注销、转发、重试、回退和销毁清理逻辑前，必须评估重复消费、消息丢失、监听泄漏和资源泄漏风险。

## 4. 测试要求

1. 测试必须覆盖本次改动点的成功路径、失败路径、异常路径、边界条件和并发风险。
2. 如果功能只有在 Spring Boot 应用运行后才能正确验证，例如自动配置、BeanPostProcessor、Redisson Bean 装配、监听注册、线程池生命周期、销毁清理等，测试必须模拟真实 Spring Boot 应用启动后的运行形态，优先使用 `@SpringBootTest` 或等价集成测试。
3. 涉及生产兼容性的修复，必须补充回归测试证明旧行为仍然正确。
4. 涉及高并发、资源释放、重试、缓存刷新、订阅去重等逻辑，必须补充能验证关键风险的测试。
5. 模块级测试命令必须保持可执行：`mvn -pl leaf-base-redisson test`。

优先覆盖以下关键能力：

1. `GXRedissonSpringDataConfig` / `GXRedissonMQConfig` 的配置解析、默认值和非法配置分支。
2. `GXRedissonMQUtils` 的订阅去重、强制订阅、取消订阅、本地缓存清理行为。
3. `GXRedissonDelayMQPostProcessor` 的转发成功、超时重试、回退入队、销毁清理流程。
4. `GXRedissonCacheServiceImpl` 的 TTL 刷新、批量写入、参数校验和边界值。
5. `GXRedissonUtils` 的锁、计数器、限流、TTL 和异常封装行为。

## 5. 变更前检查清单

提交或交付前必须确认：

1. 是否只修改了 `leaf-base-redisson` 当前 Maven 模块内的文件。
2. 是否保持生产环境已使用的对外接口规范和行为兼容。
3. 是否确认本次完善没有改变已有逻辑的正确性和既有业务语义。
4. 是否检查并补齐了本次改动点的测试覆盖。
5. 是否遵循测试驱动最佳实践，并用测试锁定回归风险。
6. 是否新增或修改了非 ASCII 日志文本。
7. 是否引入了不必要的方法或类抽取。
8. 是否移除了冗余注释，并清理了冗余 Javadoc。
9. 是否为复杂方法、复杂类或对外扩展点补充了必要 Javadoc 和使用示例。
10. 是否评估了性能、资源释放、并发可见性和线程安全风险。
11. 是否在适用场景优先考虑虚拟线程。
12. 是否影响 `redissonClient`、`redissonMQClient`、`RedissonSpringCacheManager` 的装配语义。
13. 是否影响可靠主题订阅键生成规则和幂等注册行为。
14. 是否影响延迟队列转发失败后的重试、回退和清理策略。

## 6. AGENTS.md 自动触发更新时机

出现以下任一情况时，必须在同一 PR 或提交中同步更新本文件：

1. 模块职责边界变化，例如新增、移除或迁移核心能力。
2. 目录结构变化，例如新增关键包、迁移核心类、删除关键组件。
3. 对外契约变化，例如服务接口、监听接口、注解参数、配置项、异常语义变化。
4. Redisson 连接配置或默认值策略变化，例如地址解析、单机/集群判定、线程参数、鉴权字段变化。
5. 可靠主题策略变化，例如订阅键规则、重复订阅控制、取消订阅、缓存清理、销毁流程变化。
6. 延迟队列策略变化，例如监听注册、转发、重试、失败回退、延迟时间、销毁清理流程变化。
7. 测试策略变化，例如新增必须的 Spring Boot 集成测试形态、测试基线或测试命令变化。
8. 团队新增了需长期遵守的开发约束，例如日志、测试、文档、兼容性、性能、线程模型规则。
9. 生产兼容性、性能、线程安全或资源释放要求发生变化。

## 7. 提交说明建议

1. 涉及配置装配、监听注册、延迟转发链路的变更，PR 描述必须说明行为变化和兼容性影响。
2. 涉及重试、回退、幂等订阅、资源释放等可靠性策略调整时，PR 描述必须包含风险评估和回滚方案。
3. 提交前确认新增和修改的日志均为 ASCII。
4. 提交前确认测试已覆盖改动点，并在 PR 中说明关键验证结果。
